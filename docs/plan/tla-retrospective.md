# 把 TLA+ 落进 0.22：实践、事故与反思

这篇不是模型说明，是这次把 TLA+ 从“设计稿里的一句话”落到九个模型、约 215 个配置、CI 和追踪表的过程记录。成功的部分不多说，主要写我们踩到的坑和改过的判断。

## 一、起点不是写模型，是先定“要证明什么”

一开始最容易犯的错，是打开编辑器就写 `Init`/`Next`。我们最后用的顺序是：

1. 先在设计稿和 issue #613 里找“承诺”：哪些行为是跨进程、会交错、会重试、会断线、会崩溃的。
2. 再把承诺写成性质：安全性和活性分开，能写成不变式的写不变式，写不成的明确写“不建模”。
3. 最后才决定参与者、消息、失败模型和边界。

这样做之后，模型里每个性质都能指回一条设计规则；指不回去的，基本就是“实现细节”，不应该进 TLA。

## 二、三批模型，越往后越发现“第一版通过”不算什么

第一批是事件关闭、行生命周期、调用生命周期的初版。它们能跑，性质也能过，但后来回头看，覆盖很浅：很多配置只验证了正常路径，变异配置也只是“改一个布尔值”。

第二批补 shuttle、trace、属性测试时，TLA 开始暴露实现问题：`events/link.rs` 的旧代次回插、Kotlin `RutisApp` 的起停竞态、Node/Bun 的 5 秒强杀。这些不是“模型写错了”，是模型把代码里的真实窗口放大了。

第三批把六个目录扩到设计稿范围，才真正遇到状态空间、CI 超时和“模型自己也会骗人”的问题。

## 三、几个具体的坑

### 1. 状态空间不是越大越好

`events` 的 `table-healthy` 一开始跑到 10 分钟、9 GB，`cross-runtime-sync` 的 `policy-b-posts` 有 1400 万状态，直接把 4 核 CI 的 30 分钟任务跑超时。

最后的处理不是“加机器”，而是缩小边界：2 运行时 × 1 行、`MaxDispatch=1`、加 `SYMMETRY`；`policy-b-posts` 的 `MaxDepth` 从 3 降到 2，状态从 1400 万降到 115 万。性质没变，反例还在，CI 从超时变成 7 分钟。

这件事的教训是：**TLC 的边界是设计的一部分，不是事后调参。** 每个配置都要问“这个边界下还能不能出现我想抓的反例”；不能，就换配置，不要硬跑。

### 2. 模型自己会错，而且错得很安静

`peer-rows` 的 `PFailed` 把一个变量同时写进赋值和 `UNCHANGED`，动作恒为假。结果“失败重启”路径从来没被走过，配置照样显示通过。

`row-lifecycle` 的一次重写也把 `cleanCount` 放进了不该放的 `UNCHANGED`，旧状态数看起来没变，实际覆盖已经变了。

这类错误不会让 TLC 报错，只会让模型“通过得没有意义”。后来我们加了两条习惯：

- 每个新动作至少做一次可达性检查：它真的能发生吗？
- 每个“通过”的配置，至少有一个变异配置能在同一性质上失败。

### 3. 模型配置描述的可能是旧代码

`cross-runtime-sync` 的 `bail-policy-b` 一直显示死锁。我们差点直接去改 `waits.rs`。实际打印 `forward` 的输入才发现：当前合规运行时已经把分发调用号放进监听器调用的 `path`，等价于 `bail-recorded`；`bail-policy-b` 描述的是修复前的行为。

模型没有错，错的是“把模型里的当前配置当成当前代码”。后来每个模型 README 都区分：基础配置对应哪版行为、变异配置是修复前还是故意写错。

### 4. 模型结论直接改代码，可能把真实现改坏

`async-policy-b` 说“已标记链上的异步调用记一跳”会误拒。按模型改成“只把 `sync` 当跳”之后，对象中继的 `a_synchronous_cycle_through_objects_is_refused` 直接挂住。原因是帧上只有 `sync`，分不清“发出即不管”和“之后才 `await`”。

我们最后回退了代码，把这条记成已知误报，并开了 #1098。这个决定不好看，但比“模型说对、代码改坏”好。

### 5. 真 bug、疑似 bug、设计缺口要分开

这一轮确认并修掉的真 bug 是：

- `events::link::accept` 旧代次回插；
- Kotlin `RutisApp` 起停竞态；
- Node/Bun 接管强杀早于清理截止。

疑似但还没确认的，开了 #1101/#1102/#1103；设计没定的，开了 #1098/#1099/#1100。没有把“疑似”写成“已修”，也没有把“设计没定”硬塞进某个实现补丁。

## 四、我们最后怎么判断 TLA 覆盖够不够

不是看模型数量，也不是看配置数量，而是四条：

1. 每条承诺有没有对应性质；
2. 每个性质有没有健康配置和能抓住错误的反例配置；
3. 结果有没有进 `expected.txt`、`run.sh` 和追踪表；
4. 边界、简化、未覆盖有没有写清楚。

四条齐了才算“覆盖”，缺一条就是“部分验证”。明确不保证可以接受；没写清楚才是缺口。

## 五、反思

- **TLA 是设计工具，不是代码证明。** 它能证明“在这个有界模型里没找到反例”，不能证明 Rust/Kotlin/Node 代码正确。代码要靠 trace、shuttle、一致性测试和普通测试。
- **LLM 可以写模型，但不能替人定规格。** 模型语法能过、TLC 能跑，不代表模型对应代码；规格和边界必须人审。
- **不要追求 100% 代码路径覆盖。** 状态空间和评审成本会失控；只加新承诺、历史 bug、实现歧义、待定决策这四类。
- **CI 成本要提前算。** 大配置会把 30 分钟任务跑穿；路径过滤让普通 PR 不跑 TLA，但改 `specs/**` 的 PR 要能承受全量。
- **模型通过不是终点。** 真正的产出是：真 bug 被修、设计缺口被记录、实现疑点被确认或否定。配置数量只是过程指标。

这次最大的收获不是“九个模型”，而是把“模型结论”和“代码行为”分开：模型可以大胆假设，代码修改必须回到实现和测试。下一步如果继续，重点不是再加配置，而是把 #1098–#1103 确认掉，把 trace validation 和 Kani/Miri 补上。
