# 规则追踪表

[English](README.en.md) · [会话追踪契约](../formal-trace.md) · [保证登记表](../guarantees.md) · [质量规范](../quality-standard.md)

状态：第一版，部分覆盖。日期：2026-11-09。基准：`main` `2452baee`。
议题：[#634](https://github.com/arcships/rutis/issues/634)（0.21 的追踪表，[#776](https://github.com/arcships/rutis/issues/776)）；工作安排：[0.22 计划](../plan/formal-verification-0.22.md) WS3；字段与状态规则：形式化验证设计 §5（[设计稿](../design-formal-verification-2026-11-08.md)）。

2026-11-09 同日更新：#1025 的核心已由 WS1 落地（marker 发布、`Entry::live`、确定性竞态测试、shuttle 模型），计划 §3 的 G3、G4 两条阻断解除；`ECA-*` 行按实际证据改为 5 条「部分验证」，其余仍是「未验证」。

本目录把 rutis 承诺的每条规则登记成一行：现行来源、人话承诺、级别、适用范围、证据（具体路径、用例名或行号）、变异或反例、状态、缺口。状态的用法与[保证登记表](../guarantees.md) §3 相同。统计和证据检查由脚本计算，数字不手写：

```sh
node tools/formal-trace.mjs            # 统计各状态数量，检查证据路径、编号、词汇
node tools/formal-trace.mjs --write    # 从登记表重新生成保证行，并刷新本文件 §4 的索引
node tools/formal-trace.mjs --check    # 只检查，不打印统计
```

## 1. 这一版覆盖什么、不覆盖什么

已进表：

- **保证登记表的全部 210 行**：199 条现行、8 条已撤回、3 条不单独计数的复述编号（`core/D20`、`core/D26`、`core/D27`）。这些行由脚本从登记表的 Markdown 表格抽取，编号、级别、状态、验证列原样沿用，不凭记忆补写。
- **[会话追踪契约](../formal-trace.md) 的九类规则**（每类成功、失败、边界各一行）、§4 的 8 条追踪不变量、§1 的 9 条明确不保证：44 行，编号 `TRC-*`。
- **[事件关闭接纳设计](../design-event-close-admission-2026-11-08.md) §3 的 10 条提案规则**：编号 `ECA-*`。设计的状态是「核心已实现，验证中」（2026-11-09）：规则 1、2、5 的核心已实现，确定性用例在 `crates/rutis-loader/tests/event_close_admission.rs`，shuttle 模型在 `crates/rutis/src/fiber/shuttle_tests.rs`；规则 3、6、7、8、9 的 Loading-owner、`once`、remote-entry、跨进程与重载覆盖还没补全。本表只把有实现或用例的 5 条记「部分验证」，其余记「未验证」，不写「已验证」。计划 §3 的 G3、G4 两条阻断（`release_transient` 在 `Shared.admission` 外摘除 child；shuttle 没有切换点）已解除：摘除已在同一把锁下，marker 用 `crate::sync::AtomicBool`，模型能在发布顺序上切换。

**本版不是全量，不能据此声称规则已完整。**

- #634 的 1368 条规则清单（登记表 374 条、协议规则 994 条，另有 184 条已取代）只存在于 issue 的 7 条分区评论里，仓库没有可抽取来源（计划 §3 G2）。协议规格的前缀 `EVP`、`EVD`、`SES`、`VAL`、`TAG`、`M1`、`CHN`、`SYN`、`M2`、`MNT`、`REQ`、`RTP`、`INS`、`MSV`、`REM`、`DIA`、`APP`、`NOD` 一条都还没进表。
- 会话协议规格（`docs/protocol-session.md`，2026-11-09 由 WS2 落地，79 条 `SESS-*`：61 条当前、11 条明确不保证、7 条已取代）还没有抽进本表。它的状态词汇说的是「这条规则是否现行」，不是「有没有验证」，抽取时必须逐条重新定状态（§7 第 1 步），不能把「当前」直接写成本表的「已验证」。
- 设计文档、用户文档里没有进登记表的行为（Q3.3 的实现细节除外）没有逐条抽。

所以发布门（设计 §5、质量规范 Q13.1）**不能按本表判断完成**。本表现在能做的是：说清每条已登记规则的来源、证据和缺口，把「未验证」和「明确不保证」数出来，并让证据路径可核对。

## 2. 编号

| 编号形式 | 来源 | 例子 | 规则 |
| --- | --- | --- | --- |
| `<族>/<名字>` | 保证登记表 | `core/D6`、`bridge/in-flight-call-fails-once` | 原样沿用登记表编号，不改写、不复用；撤销的行保留 |
| `TRC-<类别>-<序号>` | 会话追踪契约 §3 | `TRC-GREET-2` | 类别：`LIFE`（会话与 row 生命周期）、`FRAME`、`GREET`、`REF`、`CANCEL`、`ERR`、`LIMIT`、`MALFORMED`、`NET`；`1` 成功、`2` 失败、`3` 边界 |
| `TRC-INV-<n>` | 会话追踪契约 §4 | `TRC-INV-2` | 八条追踪不变量 |
| `TRC-NG-<n>` | 会话追踪契约 §1「不作保证」列 | `TRC-NG-4` | 明确不保证 |
| `ECA-<n>` | 事件关闭接纳设计 §3 | `ECA-4` | 设计里的规则号 |

编号只增不改：条目移动章节、改名、换文件时编号不变；删除条目时行保留并写状态与原因。

## 3. 字段与状态

| 字段 | 含义 | 谁写 |
| --- | --- | --- |
| 编号 | 见 §2 | 登记表行由脚本写；`TRC`/`ECA` 行手写 |
| 现行来源 | 现在有效的规格、设计或用户文档与章节；登记表行写 `guarantees.md §<节>`，并带上登记表的「出处」列 | 脚本 |
| 人话承诺 | 用户能观察到的成功、失败、范围和恢复；登记表行用「内容」列原文 | 脚本（登记表行）/ 手写（`TRC`/`ECA`） |
| 级别 | 核心承诺、契约行为、明确不保证（质量规范 §3） | 脚本（登记表行）/ 手写 |
| 适用范围 | 适用实现（Rust、Node、Bun、Python、Go、Swift、Kotlin）与承载、平台 | **待补**：登记表不记录适用范围，本版 210 行都写「未登记」；`TRC`/`ECA` 行按原文填写 |
| 证据 | 模型、测试、trace、属性/模糊、黑盒、计时的具体路径、用例名或行号 | 脚本（登记表行用「验证」列原文）/ 手写 |
| 变异或反例 | 验证抓到过的 bug，或故意注入的错误 | **待补**：登记表行全部「未登记」；会话追踪契约 §4 描述的变异写在对应行里 |
| 状态 | 已验证、部分验证、未验证、明确不保证；已撤回和不单独计数不计入统计 | 脚本（登记表行）/ 手写 |
| 缺口 | 下一步 issue；不能把「未覆盖」写成「通过」 | 登记表行初始值取「说明」列，之后可手工补充 |

**关于「明确不保证」行**：按登记表的惯例（如 `core/D15`），级别与状态都是「明确不保证」，不计入未验证数。会话追踪契约 §1 的 9 条明确不保证按这条惯例登记。

**状态的边界**：模型通过只把模型列为通过；必须有实现证据才能把规则写「已验证」。本表引用 `TRC`/`ECA` 行时，只有具名测试断言了要点才算「部分验证」，只有源码或注释的记「未验证」。

## 5. 怎么维护

- **改登记表或加测试**：跑 `node tools/formal-trace.mjs --write`，再 `--check`。`--write` 只改自动列，人工列按编号保留。
- **新增 `TRC`/`ECA` 行**：手写在本目录 `rules/` 的对应文件里，用同一套列；`--check` 会检查编号形式、状态词汇和证据路径。
- **改条目位置**：编号不变，只改「现行来源」和索引。
- **CI**：还没接（WS8）。接上之前，这两个命令由改动者手动跑。
- **英文**：规则行的自动列来自中文登记表，人工列与 `TRC`/`ECA` 行目前只有中文；英文登记表（`docs/guarantees.en.md`）有同编号的条目，编号可以直接对上。英文规则行是缺口（#634）。

## 6. 本版发现的缺口

1. **证据检查的一个真实缺口**：`loader/remote-runtime-lease`（唯一「未验证」的核心承诺）的验证列写 `rutis-loader/tests/leases.rs`，该文件已随连接插件删除（`ec47944c`），登记表 §16 也注明了「待补」。检查器按与 `tools/check-guarantees.mjs` 相同的规则跳过括号里的路径（那里是「说明没有证据」，不是证据），所以它落在已知的检查盲区里；补测试后这一行才能改状态。
2. **登记表 §16 的合计与表内行数不一致**：§16 写 194 条现行，表内有 199 条；按节核对是 §10 多 1 条、§12 多 2 条、§14 多 2 条。本表按表内行计数，§16 需要维护者核对。
3. **`TRC-GREET-3`（缺少必需能力时拒绝）没有用例**：源码在 `crates/rutis-bridge/src/session/plugin/greet.rs:33-70`，检索 `Incompatible` 只找到版本与承载用例。
4. **`TRC-INV-2`（握手门）Rust 侧没有断言**：异常文本 `protocol handshake incomplete` 有实现、没有用例；Go 的 `TestACallBeforeTheHandshakeEndsTheSession` 只断言自己的文字。
5. **适用范围与变异两列基本是空的**：它们的来源是支持矩阵（质量规范 §10）和各 issue 的变异结果，等 #624、#630、#631 的产物。
6. **协议规则一条都没进表**：见 §1，下一步见 §7。

## 7. 下一步：把 1368 条规则抽进来

1. **先抽现有规格**：`docs/protocol-session.md` 已经声明自己是 #634 `session` 分区的抽取来源，79 条 `SESS-*` 可以马上进表。抽取时逐条重新定状态，不照搬规格词汇：
   - 规格的「当前」→ 本表默认「未验证」，只有当证据里有一个具名测试断言了这条规则的要点时才记「部分验证」；规格里的代码行号只是实现位置，不算断言。
   - 规格的「明确不保证」→ 级别与状态都记「明确不保证」。
   - 规格的「已取代」→ 状态记「已撤回」，并在缺口写取代它的规则号；统计时不计入。
   文件建议 `rules/protocol-session.md`，列与现有九列一致；`--check` 增加对这份文件的漂移检查（规格改了而表没跟上时报出来）。
2. **再补历史清单**：把 #634 的 7 条分区评论（`registry-1`、`registry-2`、`events`、`session` 上/下、`runtime`、`remote`）导成 `rules/protocol-<分区>.md`，每行保留编号（`<前缀>-<章节>-<序号>`）、来源、规则、参与方、手段、现有形式化、状态、归属 issue、备注。
3. **扩脚本**：
   - 新增一个分区文件格式（列与现有九列对齐，`现有形式化` 与 `归属 issue` 合并进「证据」「缺口」）；
   - 把 issue 的状态词汇（`已覆盖`/`部分`/`未覆盖`/`不适用`/`明确不保证`/`未登记`/`已取代`）映射到本表的「状态」，映射表写进 §3；
   - 生成 `protocol-*` 文件时保留已取代的行，统计时不计入；
   - `--check` 增加两条：协议行的编号格式，和与区块合计的一致性（#634 的统计表）。
4. **对账而不是照抄**：issue 的清单按 `3496669b` 抽，0.17–0.19 的 11 份设计稿和 #635 的新规格要按现行文本重抽；重抽前，协议行的状态记「未验证」并注明「按 issue 评论抽取、未按现行规格复核」。
5. **接上模型与一致性用例**：等 WS4（`#613`）、WS5（`#624`）、WS7（`#631`）产出后，把 TLA+ 性质、trace 验证器、一致性用例名写进证据列，状态才能从「未验证」上调。
6. **接 CI**：`--check` 进 PR；#776 要求的「追踪表引用」检查就是它，「模型漂移」检查在 WS4/WS8。
