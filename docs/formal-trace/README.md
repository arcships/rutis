议题：[#634](https://github.com/arcships/rutis/issues/634)（0.21 的追踪表，[#776](https://github.com/arcships/rutis/issues/776)）；工作安排：[0.22 计划](../plan/formal-verification-0.22.md) WS3；字段与状态规则：形式化验证设计 §5（[设计稿](../design-formal-verification-2026-11-08.md)）。

本目录把 rutis 承诺的每条规则登记成一行：现行来源、人话承诺、级别、适用范围、证据（具体路径、用例名或行号）、变异或反例、状态、缺口。状态的用法与[保证登记表](../guarantees.md) §3 相同。统计和证据检查由脚本计算，数字不手写：

```sh
node tools/formal-trace.mjs            # 统计各状态数量，检查证据路径、编号、词汇
node tools/formal-trace.mjs --write    # 从登记表重新生成保证行，并刷新本文件 §4 的索引
node tools/formal-trace.mjs --check    # 只检查，不打印统计
```

## 3. 字段与状态

| 字段 | 含义 | 谁写 |
| --- | --- | --- |
| 编号 | 见 §2 | 登记表行由脚本写；`TRC`/`ECA` 行手写；协议行由 issue 导出 |
| 现行来源 | 现在有效的规格、设计或用户文档与章节；登记表行写 `guarantees.md §<节>`，并带上登记表的「出处」列 | 脚本 |
| 人话承诺 | 用户能观察到的成功、失败、范围和恢复；登记表行用「内容」列原文 | 脚本（登记表行）/ 手写（`TRC`/`ECA`） |
| 级别 | 核心承诺、契约行为、明确不保证（质量规范 §3） | 脚本（登记表行）/ 手写 |
| 适用范围 | 适用实现（Rust、Node、Bun、Python、Go、Swift、Kotlin）与承载、平台 | **待补**：登记表不记录适用范围，211 行登记表行都写「未登记」；`TRC`/`ECA` 行按原文填写；协议行填 issue 的「参与方」（跨进程、进程内并发、纯逻辑、外部），不是实现矩阵 |
| 证据 | 模型、测试、trace、属性/模糊、黑盒、计时的具体路径、用例名或行号 | 脚本（登记表行用「验证」列原文）/ 手写；协议行用 issue 的「现有形式化」列 |
| 变异或反例 | 验证抓到过的 bug，或故意注入的错误 | **待补**：登记表行全部「未登记」；会话追踪契约 §4 描述的变异写在对应行里 |
| 状态 | 已验证、部分验证、未验证、明确不保证；已撤回和不单独计数不计入统计 | 脚本（登记表行、协议行）/ 手写 |
| 缺口 | 下一步 issue；不能把「未覆盖」写成「通过」 | 登记表行初始值取「说明」列，之后可手工补充；协议行取「归属 issue」+「备注」+ 降级原因 |

**关于「明确不保证」行**：按登记表的惯例（如 `core/D15`），级别与状态都是「明确不保证」，不计入未验证数。会话追踪契约 §1 的 9 条明确不保证按这条惯例登记。

**状态的边界**：模型通过只把模型列为通过；必须有实现证据才能把规则写「已验证」。本表引用 `TRC`/`ECA` 行时，只有具名测试断言了要点才算「部分验证」，只有源码或注释的记「未验证」。

**协议行（`rules/protocol-*.md`）的映射。** 这些文件保留 issue 的十列和 issue 的状态词，脚本读入时换成九列，映射只降不升：

| issue 状态 | 本表状态 | 规则 |
| --- | --- | --- |
| 已覆盖 | 已验证 / 部分验证 | 只有「手段」含实现检查（`K`、`PT`、`FZ`、`TV`、`SH`、`KANI`、`测试`）、「现有形式化」有具名条目、且这些文件在当前树都能找到时，才记「已验证」；只有 TLA/模型、没有具名条目或证据文件找不到的，记「部分验证」 |
| 部分 | 部分验证 | 不因为 issue 说「部分」就上调 |
| 未覆盖 | 未验证 / 明确不保证 | 规则文字本身写「明确不保证」的 6 条记「明确不保证」，其余记「未验证」 |
| 不适用 | 明确不保证 / 不单独计数 | 备注写明明确不保证的 35 条记「明确不保证」；其余 214 条只靠测试、形式化够不着，记「不单独计数」，原因写进缺口 |
| 明确不保证 | 明确不保证 | 级别与状态一致 |
| 未登记 | 未验证 | 缺口写「未登记（测试里用了、登记表没有）」 |
| 已取代 | 已撤回 | 保留行，统计时不计入 |

九列的对齐方式：编号=`编号`；现行来源=`来源`；人话承诺=`规则`；级别=明确不保证或契约行为（issue 没有级别列，除明确不保证外不冒充核心承诺）；适用范围=`参与方`；证据=`现有形式化`；变异或反例=`未登记`（issue 没有这一列）；状态=上表映射；缺口=`归属 issue` + `备注` + 降级原因。`对应` 列留在协议文件里，用来看它对应哪条保证登记表编号，不进九列。协议行没有按现行规格复核，所以即使记「已验证」，也只表示 issue 快照里有具名实现证据，不表示当前树上重跑过。

## 5. 怎么维护

- **改登记表或加测试**：跑 `node tools/formal-trace.mjs --write`，再 `--check`。`--write` 只改保证行的自动列、人工列按编号保留，并刷新 §4 的索引；它不碰 `rules/protocol-*.md`。
- **改协议清单**：从 #634 对应评论重新导出表格，保留十列、编号和备注；不要在导出文件里手改状态，映射由脚本做。`--check` 检查十列、编号形式、分区合计（156/9、218/0、253/9、246/104、264/45、231/17，合计 1368/184）、issue 状态词汇、重复编号和证据路径。
- **新增 `TRC`/`ECA` 行**：手写在本目录 `rules/` 的对应文件里，用同一套列；`--check` 会检查编号形式、状态词汇和证据路径。
- **改条目位置**：编号不变，只改「现行来源」和索引。
- **CI**：还没接（WS8）。接上之前，这两个命令由改动者手动跑。
- **英文**：规则行的自动列来自中文登记表，人工列与 `TRC`/`ECA` 行目前只有中文；协议清单的表格也是中文。英文登记表（`docs/guarantees.en.md`）有同编号的条目，编号可以直接对上。英文规则行是缺口（#634）。

## 6. 本版发现的缺口

1. **1368 条协议规则没有按现行规格复核**：全部来自 #634 的 `3496669b` 快照。WS2 的 `docs/protocol-session.md` 已有 82 个 `SESS-*` 编号，但它的「当前/明确不保证/已取代」说的是规则是否现行，不是有没有验证；要逐条重抽、重新定状态，不能把「当前」直接写「已验证」。0.17–0.19 的 11 份设计稿也要按现行文本重抽；#634 的第 8 条评论（`6415164837`）还说明远程运行时在 0.19 按 #695 补齐一致性、link 与远程租约的规则不变，`protocol-remote.md` 也没有逐条体现这次变化。
2. **10 个裸文件名引用在当前树找不到**（7 个名字、7 行，全部在协议清单的「现有形式化」列）：`events-conformance.test.mjs`、`test_events_conformance.py`、`events-conformance.test.ts`、`node_conformance.rs`、`websocket_conformance.rs`、`leases.rs`（3 行）、`memory_mux.rs`（2 行）。这些行都只记「部分验证」；补上现行路径或新用例后才能上调。备注列里还有已不存在的路径（抽查到 `crates/rutis-bridge/src/cordis/server.rs`、`go/rutis/dial.go`、`runtime/plugin.rs`），`--check` 目前只查「现有形式化」列，重抽时要一并处理。
