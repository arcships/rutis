本目录把 rutis 承诺的每条规则登记成一行：现行来源、人话承诺、级别、适用范围、证据（具体路径、用例名或行号）、变异或反例、状态、缺口。状态的用法与[保证登记表](../guarantees.md) §3 相同。统计和证据检查由脚本计算，数字不手写：

```sh
node tools/formal-trace.mjs            # 统计各状态数量，检查证据路径、编号、词汇
node tools/formal-trace.mjs --write    # 从登记表重新生成保证行，刷新 §4 的索引与复核表
node tools/formal-trace.mjs --check    # 只检查，不打印统计
```

- **状态按复核定，不按 issue 的「已覆盖」定**：口径是来源是否还在、有没有现行锚点、`现有形式化` 列的证据是否解析、状态只降不升（[复核表](recheck-0.22.md) §1）。161 条对到 `docs/protocol-session.md` 的 `SESS-*`；261 条没有现行来源（多语言运行时设计的 0.9 基线、远程插件设计、登记表已删的行等），按原因列在复核表 §5。规格写「当前」只说明规则现行，不等于本表的「已验证」。
- **80 个协议清单编号与保证登记表的行同号**（例如 `core/D1`、`bridge/value-roundtrip`）；两份清单的粒度不同（协议清单有 `core/D2a`/`D2b` 这种拆行），本表把它们当两行保留。**1817 是行数，不是不同的规则数**，不要把保证登记表和协议清单的合计相加。
- 设计文档、用户文档里没有进登记表、也没有进 #634 清单的行为（Q3.3 的实现细节除外）没有逐条抽。

所以发布门（设计 §5、质量规范 Q13.1）**不能按本表判断完成**：261 条协议规则没有现行来源，201 条不单独计数，证据列里还有 10 个裸文件名在当前树找不到（7 行，见 §6）。本表现在能做的是：说清每条已登记规则的来源、证据和缺口，把「未验证」「明确不保证」「已撤回」数出来，并让证据路径可核对。

## 3. 字段与状态

| 字段 | 含义 | 谁写 |
| --- | --- | --- |
| 编号 | 见 §2 | 登记表行由脚本写；`TRC`/`ECA` 行手写；协议行由 issue 导出 |
| 现行来源 | 现在有效的规格、设计或用户文档与章节；登记表行写 `guarantees.md §<节>`，并带上登记表的「出处」列 | 脚本 |
| 人话承诺 | 用户能观察到的成功、失败、范围和恢复；登记表行用「内容」列原文 | 脚本（登记表行）/ 手写（`TRC`/`ECA`） |
| 级别 | 核心承诺、契约行为、明确不保证（质量规范 §3） | 脚本（登记表行）/ 手写 |
| 适用范围 | 适用实现（Rust、Node、Bun、Python、Go、Swift、Kotlin）与承载、平台 | **待补**：登记表不记录适用范围，211 行登记表行都写「未登记」；`TRC`/`ECA` 行按原文填写；协议行填 issue 的「参与方」（跨进程、进程内并发、纯逻辑、外部），不是实现矩阵 |
| 证据 | 模型、测试、trace、属性/模糊、黑盒、计时的具体路径、用例名或行号 | 脚本（登记表行用「验证」列原文）/ 手写；协议行用 issue 的「现有形式化」列 |
| 变异或反例 | 验证抓到过的 bug，或故意注入的错误 | **待补**：登记表行全部「未登记」；会话追踪契约 §4 描述的变异写在对应行里 |
| 状态 | 已验证、部分验证、未验证、明确不保证；已撤回和不单独计数不计入统计 | 脚本（登记表行；协议行按[复核表](recheck-0.22.md)的结论）/ 手写 |
| 缺口 | 下一步 issue；不能把「未覆盖」写成「通过」 | 登记表行初始值取「说明」列，之后可手工补充；协议行取「归属 issue」+「备注」+ 降级原因 |

**关于「明确不保证」行**：按登记表的惯例（如 `core/D15`），级别与状态都是「明确不保证」，不计入未验证数。会话追踪契约 §1 的 9 条不作保证条目按这条惯例登记；`TRC-GREET-3` 因实现里没有入口（#1111）也按同一惯例记；`TRC-NG-4` 已按协议 4 撤回（#1123），不计入。

**状态的边界**：模型通过只把模型列为通过；必须有实现证据才能把规则写「已验证」。本表引用 `TRC`/`ECA` 行时，只有具名测试断言了要点才算「部分验证」，只有源码或注释的记「未验证」。

**协议行（`rules/protocol-*.md`）的映射。** 这些文件保留 issue 的十列和 issue 的状态词，脚本读入时换成九列，映射只降不升：

| issue 状态 | 本表状态 | 规则 |
| --- | --- | --- |
| 已覆盖 | 已验证 / 部分验证 | 只有「手段」含实现检查（`K`、`PT`、`FZ`、`TV`、`SH`、`KANI`、`测试`）、「现有形式化」有具名条目、且这些文件在当前树都能找到时，才记「已验证」；只有 TLA/模型、没有具名条目或证据文件找不到的，记「部分验证」 |
| 部分 | 部分验证 | 不因为 issue 说「部分」就上调 |
| 未覆盖 | 未验证 / 明确不保证 | 规则文字本身写「明确不保证」的 6 条记「明确不保证」，其余记「未验证」 |
| 不适用 | 明确不保证 / 不单独计数 | 备注写明明确不保证的 35 条记「明确不保证」；其余 214 条只靠测试、形式化够不着，记「不单独计数」，原因写进缺口 |
| 明确不保证 | 明确不保证 | 级别与状态一致 |
| 未登记 | 未验证 | 缺口写「未登记（测试里用了、登记表没有）」 |
| 已取代 | 已撤回 | 保留行，统计时不计入 |

九列的对齐方式：编号=`编号`；现行来源=`来源`；人话承诺=`规则`；级别=明确不保证或契约行为（issue 没有级别列，除明确不保证外不冒充核心承诺）；适用范围=`参与方`；证据=`现有形式化`；变异或反例=`未登记`（issue 没有这一列）；状态=上表映射再经复核；缺口=`归属 issue` + `备注` + 降级原因。`对应` 列留在协议文件里，用来看它对应哪条保证登记表编号，不进九列。

**复核层（2026-11-11）。** 上表是 issue 快照的映射，是本表的上限，不是最终状态。协议行的状态还要过[复核表](recheck-0.22.md) §1 的四件事：来源是否还在、有没有现行锚点、证据是否解析、登记表是否已撤回这一行。复核只降不升：0.19 / 0.22 删掉的机制（compat、`events-v2`、`sync-wait`、节点 `export` / `import`、`Registration`、接入点、`Revocations`、`PeerRows`、`peer:`、`runtimes.remote`、`Transport`、`ChannelInfo`）与登记表已撤回的行记「已撤回」；来源是历史设计、没有现行锚点的行不再记「已验证」。协议行的规则文字没有逐条重写，语义重抽只完成了 `TRC` 分区（44 行）；`rules/protocol-*.md` 保持 issue 的十列原文，复核结论只在本表和复核表里。

## 5. 怎么维护

- **改登记表或加测试**：跑 `node tools/formal-trace.mjs --write`，再 `--check`。`--write` 只改保证行的自动列、人工列按编号保留，刷新 §4 的索引与[复核表](recheck-0.22.md)；它不碰 `rules/protocol-*.md`。
- **改协议清单**：从 #634 对应评论重新导出表格，保留十列、编号和备注；不要在导出文件里手改状态，映射由脚本做。`--check` 检查十列、编号形式、分区合计（156/9、218/0、253/9、246/104、264/45、231/17，合计 1368/184）、issue 状态词汇、重复编号和证据路径。
- **改现行来源或复核结论**：改 `tools/formal-trace-recheck.mjs` 的 `SOURCES`（每个前缀的现行文档）、`ANCHORS`（旧章节对到 `SESS-*`）、`SUPERSEDED`（被删除的规则与依据）、`UNMAPPED`（没有现行来源的原因），再 `--write`。`--check` 会核对锚点在 `docs/protocol-session.md` 里、`SUPERSEDED` 的编号是协议行、依据文件存在，以及复核表与生成结果一致。
- **改语义重抽的 TRC 行**：同时改 `rules/trace-contract.md` 与 `tools/formal-trace-semantic.mjs` 里同编号的条目（英文规则、英文缺口、来源章节、锚点），再 `--write`。`--check` 核对：两边的编号一一对应、每个锚点在 `docs/protocol-session.md` 里并出现在该行「现行来源」、来源章节在两个数据模块的文档里存在、没有锚点的行写了原因，以及中文复核表 §5 与英文复核页逐字一致。数据分属三个文件：`formal-trace-recheck.mjs`（来源、锚点区间、撤回、无来源原因、备注、登记表族）、`formal-trace-semantic.mjs`（语义重抽）、`formal-trace.mjs`（列与状态词汇、文件清单）；后者的 `--check` 第 0 步核对这些字面量一致（族清单、前缀清单、`SOURCES` 的文档存在）。
- **新增 `TRC`/`ECA` 行**：手写在本目录 `rules/` 的对应文件里，用同一套列；`--check` 会检查编号形式、状态词汇和证据路径。
- **改条目位置**：编号不变，只改「现行来源」和索引。
- **CI**：还没接（WS8）。接上之前，这两个命令由改动者手动跑。
- **英文**：规则行的自动列来自中文登记表，人工列与 `TRC`/`ECA` 行目前只有中文；协议清单与复核表也是中文。英文登记表（`docs/guarantees.en.md`）有同编号的条目，编号可以直接对上。英文规则行是缺口（#634）。

## 6. 本版发现的缺口

1. **261 条协议规则没有现行来源**：会话层有 `docs/protocol-session.md`（82 条 `SESS-*`，161 条规则对到它）；事件有 2026-10-18 的协议规格（0.19 未同步，`events-v2` 与节点名单的规则按 0.19 撤回）；运行时、挂载、远程仍是 0.17–0.19 的设计稿或用户指南，没有按 0.22 重写的规格。多语言运行时设计（`SYN`）与远程插件设计（`REM`）的来源本身就是历史方案，按原因列在[复核表](recheck-0.22.md) §5；写规格是 #635 的后续。
2. **10 个裸文件名引用在当前树找不到**（7 个名字、7 行，全部在协议清单的「现有形式化」列）：`events-conformance.test.mjs`、`test_events_conformance.py`、`events-conformance.test.ts`、`node_conformance.rs`、`websocket_conformance.rs`、`leases.rs`（3 行）、`memory_mux.rs`（2 行）。这些行都只记「部分验证」或「未验证」；补上现行路径或新用例后才能上调。备注列里还有已不存在的路径（抽查到 `crates/rutis-bridge/src/cordis/server.rs`、`go/rutis/dial.go`、`runtime/plugin.rs`），`--check` 目前只查「现有形式化」列，重抽时要一并处理。
3. **证据检查的一个真实缺口**：`loader/remote-runtime-lease`（唯一「未验证」的核心承诺）的验证列写 `rutis-loader/tests/leases.rs`，该文件已随连接插件删除（`ec47944c`），登记表 §16 也注明了「待补」。检查器按与 `tools/check-guarantees.mjs` 相同的规则跳过括号里的路径（那里是「说明没有证据」，不是证据），所以它落在已知的检查盲区里；补测试后这一行才能改状态。
4. **登记表 §16 的合计与表内行数不一致**：§16 写 194 条现行，表内有 200 条；按节核对是 §10 多 1 条、§12 多 2 条、§14 多 2 条。本表按表内行计数，§16 需要维护者核对。
5. **`TRC-INV-2`（握手门）Rust 侧没有断言**：异常文本 `protocol handshake incomplete` 有实现、没有用例；Go 的 `TestACallBeforeTheHandshakeEndsTheSession` 只断言自己的文字。
6. **适用范围与变异两列基本是空的**：它们的来源是支持矩阵（质量规范 §10）和各 issue 的变异结果，等 #624、#630、#631 的产物。协议行的「适用范围」填的是 issue 的参与方，不是实现矩阵；「变异或反例」全部「未登记」。
7. **语义重抽只完成 TRC 分区**：44 行追踪规则已按现行来源重写；协议清单的 1368 条仍只有复核（来源、锚点、证据、状态），没有重写规则文字。复核表 §4 的每一行都注明了它落在哪条 `SESS-*` 或哪份现行文档；没有锚点的行在 §6。
