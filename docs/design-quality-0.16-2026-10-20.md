## 三、承诺闭环

### 3.1 登记表补齐与自动核对

补齐三类条目：

- `loader/` 与 `host/` 剩余条目，按现状 §5 与各设计文档逐条登记；
- 新 SDK 的 `sdk/swift-*`、`sdk/kotlin-*`，至少覆盖会话、值、事件、测试工具；
- 0.16 新增的 `bridge/resource-limit`、`sdk/testing-matches-runtime` 的六实现版本。

新增 `tools/check-guarantees.mjs`，在 `checks` 任务与发布门运行：

1. 源码里的 `guarantee: <编号>` 必须对应表里的一行；表里的编号不得重复；
2. 状态为“已验证”的行至少有一个测试引用；测试引用必须能定位到仓库里的文件与测试名；
3. 状态为“部分验证 / 未验证”的行必须有 issue 号或计划章节；
4. 核心承诺行必须有“第二验证”列（见 3.2）。

脚本先以现有 194 行为基线：新增加的行与引用必须通过；存量未定位的引用进 `tools/guarantees-baseline.txt`，0.16 发布前清零。这样不会因为历史条目一次性卡住所有 PR。

### 3.2 核心承诺的双重验证

规范 Q3.1 要求核心承诺由至少两种独立方式验证。登记表只记一列“验证”，无法看出是否满足。增加一列“第二验证”，只对核心承诺填写，取值是：

- 黑盒 E2E（`tests/e2e`）；
- 模型（`specs/` 的 TLA+ 或 shuttle）；
- 另一种实现的独立测试（例如同一会话契约在 Node、Python、Go、Bun、Swift、Kotlin 各跑一遍）。

0.16 前逐条核对 41 条核心承诺。当前 4 条“部分验证”的处理：

| 条目 | 现状缺口 | 0.16 的处理 |
| --- | --- | --- |
| `core/D22` | 依赖未就绪保持 Pending 已验证；**不检测依赖环**没有测试锁定 | 加一条回归测试：互相等待的行都停在 Pending，不报错、不启动；登记为“明确不保证” |
| `core/D28` | isolate 出的 `Ctx` 保留原 fiber 所有权；isolate 所有权没有独立测试 | 加契约测试：isolate 的清理在父 fiber 卸载时恰好执行一次；再加一条黑盒或 loader 侧验证 |
| `boundary/5.8` | 未捕获异常结束进程已验证；“不加超时”没有断言 | 加测试：调用不因宿主或兼容层的超时而失败，只有调用方自己的取消生效 |
| `loader/instance-edits-all-or-none` | 全有或全无已实现，缺部分回滚路径的独立验证 | 加 dry-run 失败与部分失败两条测试，断言旧代继续运行、可编辑层未写 |

### 3.3 明确不保证的锁定

规范 Q3.4：可能被误以为保证的行为，要有测试锁定“确实不提供”。0.16 把 6 条“明确不保证”逐条对照：有测试的保留，没有的补一条最小回归测试，或在表里写明“没有测试的理由”。`core/D22` 与值的范围限制是必做；其余按同一规则处理。

### 3.4 设计文档的级别与风险

新设计文档开头必须写“级别 / 风险 / 验收”，值取自规范 §3 与 §4。历史文档不批量回填；PR 模板加一项，`checks` 只检查新加的 `docs/design-*.md` 是否有这三个字段。这样规则从 0.16 起生效，不制造一次性的文档债。

## 四、资源完整性

### 4.1 引用与调用数上限（#178 后半）

**问题。** 当前只限制单帧大小与值嵌套深度。一个插件可以无限授予引用或无限发起调用，宿主与对端的内存、任务表、引用表会一直增长；现有测试没有边界。

**协议。** hello 增加可选字段：

```json
"limits": { "refs": 4096, "calls": 1024 }
```

双方各自宣告自己愿意承担的上限。字段缺席表示“不限制”，用于 0.15 及更早的对端；0.16 一侧仍按自己的上限执行，并在错误里说明对端没有宣告。

**计数。** 每个会话、每个方向：

- `refs`：本侧已授予、尚未释放的对象或函数引用数。引用的生命周期沿用现行规则（调用结束或显式释放）；每次授予占一个引用槽，同一对象再次授予再占一个。
- `calls`：本侧已经开始、尚未结束的调用数，包含进来的调用与发出去等结果的调用；进来的调用在执行前检查，超限时不执行。

**默认值。** 每会话 4096 个存活引用、1024 个在途调用。宿主用 `--max-refs` / `--max-calls` 或 `RUTIS_MAX_REFS` / `RUTIS_MAX_CALLS` 覆盖；SDK 的 `RuntimeOptions` / `Serve` 提供同名选项。默认值在 0.16 的实现 PR 里用现有浸泡与事件矩阵的数据复核一次，只能上调，不在补丁版本下调。

**超限行为。** 上限以接收方计数为准；发送方按对端宣告预检，双方计数不一致时以接收方的错误为准。返回结构化错误 `ResourceLimit`，字段 `resource`（`"refs"` 或 `"calls"`）、`limit`、`current`：

- 发不出的引用：这次调用在发出前失败，不创建引用，会话继续；
- 进来的调用：执行前拒绝，返回错误，不占用执行线程；
- 事件参数或结果里的引用：只让这次分发失败，符合统一事件的“值发不出只影响这次调用”规则；
- **不**关闭会话、**不**静默丢弃、**不**重试。

**验收。** Rust 与六种语言实现各一组测试：在 `limit - 1`、`limit`、`limit + 1` 三个点上断言成功 / 成功 / 只失败这一次；失败后会话继续，引用表与任务数回到基线；0.15 对端不宣告上限时行为与今天相同；错误名与字段在七种实现一致。

**不做。** 按字节或内存的配额、按插件的配额、准入控制、队列长度：0.16 不做，避免一个版本里同时引入两种资源模型。

### 4.2 残余检查统一

把 `soak.rs` 里的 fd / 线程采样抽到共用模块，E2E 每个场景结束时增加：

- 宿主的 fd、线程、tokio 存活任务数回到场景开始前的基线；
- 每个运行时的 fd、线程、任务数回到基线（运行时 `inspect` 返回，见下）；
- 内核 `diagnostics()` 的 fiber、绑定、监听器、事件积压回到基线；
- 运行时的行、代理、导出槽数量回到基线。

运行时 `inspect` 扩展到 Go、Bun、Swift、Kotlin，返回统一 JSON：

```json
{ "rows": 0, "refs": 0, "calls": 0, "listeners": 0, "tasks": 0 }
```

Node / Python 已有控制方法，补齐字段即可。E2E 在场景开始与结束时各调一次；运行时已退出时只核对宿主侧。容差与理由写在 `tests/e2e/src/residue.rs`：fd 允许 +0，线程允许 +0，任务允许 +0；确实需要常驻的（例如 Node 的 esbuild 加载器）写明并单独允许。

### 4.3 后台异常

- **Rust**：`rutis-test-support` 增加后台 panic 捕获。测试作用域内派生线程或任务发生 panic 时记录，作用域结束让测试失败；预期 panic 的测试显式标记。
- **Node / Bun**：测试框架统一安装 `uncaughtException` 与 `unhandledRejection` 处理，记录并在测试结束时失败；运行时自身的“未捕获异常结束进程”不变。
- **Swift / Kotlin**：测试工具记录未处理的 Task / 协程异常，在测试结束时失败；不改变运行时行为。

验收：在六种实现里各放一个故意在后台抛异常的最小测试，必须是失败；修复后必须通过；正常运行的后台任务不被误报。

### 4.4 Windows 信号与残余

补 Windows 的 Ctrl-C 与控制台关闭两条 E2E，覆盖 `rutis-host run` 与 `dev`，断言退出码、清理与残余检查。现有的 Ctrl-Break 与 Job Object 保留。

### 4.5 dylib 预加载与多写者对账

- `design-dylib-sdk` §十三 的 5 项逐条勾选，缺的补测试或写明不适用范围；
- Q5.5.2 的多写者测试逐条核对：`save` 串行且按提交顺序、持续冲突后返回 `Conflict`、重放不再适用的修改被移出队列。缺的补进 `rutis-loader/tests/loader.rs`。

### 5.4 错误、状态与凭据

- SDK 与 bridge 库级错误增加快照：错误名、字段、消息模板；与 `rutis-host` 的逐字锁定同一套做法，不锁具体地址或时间。
- `run` / `dev` 的状态输出整体加一份快照，覆盖启动、等待、失败、停止四类行。
- 库级日志与诊断输出增加凭据扫描测试：构造带 token 的配置与连接，断言日志、trace、错误里不出现 token；E2E 的现有检查保留。

### 5.5 Swift / Kotlin 的跨版本

把 Swift 与 Kotlin 纳入 `tests/e2e/tests/cross_version.rs`：

- 0.15 的 Swift / Kotlin 运行时与 0.16 宿主相遇：正常工作，或在握手时说明升级哪一端；
- 0.16 运行时与 0.15 宿主相遇：同上；
- 事件协议版本不同时按统一事件的规则拒绝，不挂起。

SwiftPM 与 Maven 的上一版包从已发布 tag / 仓库取；取不到时测试失败，不静默跳过。

## 六、CI 与发布门

### 6.1 静态检查补齐

- `actionlint` 进 `checks`，检查全部 workflow；
- 许可证检查进 `deps.yml`：`cargo deny check licenses`、npm / PyPI 的许可证清单；新增依赖必须在 PR 描述里写理由，PR 模板加一项；
- 许可证策略写进 `docs/ci.md`，允许列表随首次运行建立，不默认全放行。

### 6.2 semver 从提示改检查

`semver-rutis` 现在只发 warning。0.16 起：检测到公开 API 的破坏性变化时，PR 必须同时把下一个 train 的 minor 版本号加一，或在 PR 里显式批准“这是允许的破坏”；否则任务失败。0.x 的规则写进 `docs/ci.md`，与发布脚本的版本检查共用一份配置。

### 6.3 普通 PR 的 10 分钟目标

先用 0.15 之后一周的数据重测（`tools/ci-stats.mjs`），再决定：

- 如果中位 ≤ 10 分钟：保留目标，增加一条回归检查（连续一周 p90 超过阈值时开 issue）；
- 如果中位 > 10 分钟：把目标改成“中位 ≤ 10 分钟、p90 ≤ 20 分钟”，并在 `docs/ci.md` 写明排队与 runner 数量的关系；同时把 `multiprocess`、`soak` 等长任务从 PR 移到 nightly（如果还没移）。

不允许既不达标也不改目标。

### 6.4 发布门

`release.md` 的发布门增加：

1. `tools/check-guarantees.mjs` 通过，基线文件为空；
2. 六个发布渠道与 release 二进制的安装冒烟全绿（未发布渠道有显式标记）；
3. 0.15 ↔ 0.16 跨版本通过；
4. 持久化样本包含 0.15、0.16；
5. 规模包络与性能参考值已更新；
6. 0.16 发布说明列出所有“明确不保证”。

### 6.5 规模与性能声明

- 发布规模包络：沿用现状 §2.2 的上限——单宿主 500 行、10 个本地运行时、20 个节点；新增每会话 4096 个引用、1024 个在途调用；值嵌套 64 层、帧 16 MiB。连续运行以 S8 的一小时无增长趋势为已验证范围，更长时间不承诺。
- 超过包络的行为不承诺；新加的引用与调用上限必须显式失败，其余记录为明确不保证。
- 性能数字统一标注“承诺”或“参考”。同步调用约 30 µs 标为参考值，附测量机器与日期；不设 CI 回归阈值，避免噪声误报。
- 更长运行时间与更大规模留给后续版本，不在 0.16 承诺。

## 十、风险与处理

| 风险 | 处理 |
| --- | --- |
| 资源上限默认值过低，误伤正常插件 | 先用现有事件矩阵与浸泡数据复核；默认值只上调；提供配置项 |
| 六种语言实现的错误名或字段不一致 | 以 Rust 侧的错误名为准，Rust 与六种语言实现各一组同名测试；跨实现一致性套件覆盖 |
| 小版本里改协议字段破坏 0.15 对端 | `limits` 可选，缺席按不限制；0.15 ↔ 0.16 跨版本测试进发布门 |
| `check-guarantees` 误报历史条目 | 基线文件 + 新条目严格；0.16 发布前清零 |
| 安装冒烟依赖未发布的渠道 | 显式标记“未发布”；发布后第一次运行必须覆盖 |
| 10 分钟目标被 runner 排队拖垮 | 用一周数据决定；达标保留，不达标改目标并写明，不静默 |
| 范围蔓延成“修所有部分验证” | 只做 P0 / P1 与核心承诺；其余登记为后续 issue，不阻塞 0.16 |
