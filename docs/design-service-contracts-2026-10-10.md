# 服务契约：同一服务的不同实现保持一致

[English](design-service-contracts-2026-10-10.en.md)

设计提案 · 关联 [#211](https://github.com/arcships/rutis/issues/211) · 对应[质量规范](quality-standard.md) Q6.9、Q6.7；[现状](quality-status.md) 场景 G，风险 G1（P0）· 相关 [#206](https://github.com/arcships/rutis/issues/206)、[#188](https://github.com/arcships/rutis/issues/188)（S4）

## 1. 问题

[设计哲学](design-philosophy.md) §四 的主线：`planner` 依赖服务名 `calendar`。`calendar` 先由 Python 插件提供，后来换到内网节点上的插件，最后换成 Rust 实现。`planner` 一行不改，宿主不重启。

内核保证的是"换了提供者，依赖它的插件停下、再启动"。内核不保证新提供者返回的数据和旧的一样。现在：

- 插件只能声明服务的方法名和方法形状（`sync` / `async`）；
- 数据形状（字段名、哪些字段可以没有、错误类型）只靠约定；
- 没有任何手段检查两个实现是否一致。

不一致的例子，都是跨语言时自然会出现的：

| 不一致 | 例子 |
| --- | --- |
| 字段名 | Python 返回 `{"start_time": ...}`，TypeScript 返回 `{startTime: ...}` |
| 对象里没有值的字段 | Python 写 `{"note": None}`（另一端收到 `null`）；TypeScript 常见的写法是干脆不放这个字段（另一端收不到 `note`） |
| 方法没有结果 | TypeScript 方法不写 `return`，线上是 `undefined`，Python 使用方收到的是 SDK 的 `UNDEFINED`；Python 方法返回 `None`，线上是 `null`，TypeScript 使用方收到 `null`。`=== undefined` 和 `is None` 的判断在切换后翻转 |
| 空结果 | 一个实现返回 `[]`，另一个返回 `null` |
| 错误 | 找不到时，一个抛 `KeyError`，一个抛 `NotFound`，一个返回 `null`；Rust 的 `native_error` 一律叫 `RustError` |
| 方法形状 | 一个实现声明 `list` 为 `sync`，另一个声明为 `async`，使用方的写法不同 |
| 集合类型 | Python 返回 tuple，另一端收到数组；返回 set，跨不过边界 |

使用方在切换后出错。出错的位置在使用方，原因在提供方，而切换又是运行中发生的。这是风险 G1：影响高（违反"使用方只依赖服务名"这条核心承诺的实际效果），可能性高（不同的人、用不同语言写实现）。

## 2. 现在有什么

| 已有 | 做什么 | 与本问题的关系 |
| --- | --- | --- |
| `provides` 声明（[插件 API](guide/plugin-api.md)） | 服务名、方法名、`sync` / `async` | 方法形状已经是契约；数据形状不是 |
| 值传递规则（插件 API "值怎样传递"） | 跨进程时什么被复制、什么按引用、什么不能跨 | 规定了线上能出现哪些值，没规定某个服务该返回哪个值 |
| SDK 测试工具（`@arcships/rutis/testing`、`rutis.testing`） | 不启动宿主就能加载插件、调用它提供的服务；严格模式按跨进程规则传值 | 只能测同一种语言的插件；期望值写在各自语言的测试代码里，别的实现用不上 |
| 运行时一致性检查（`rutis_bridge::runtime::testing`） | 一组用 Rust 写的调用和期望，对 Node 和 Python 运行时各跑一遍同一个 fixture（`conformance-weather`） | 正是"一组用例、多种实现"的做法，但只服务于运行时本身，用例写死在 Rust 里 |

最后一行说明这条路在仓库里已经走通过：同一组调用和期望，对不同语言的实现运行。本设计把它从"运行时的一致性"推广到"任何服务的一致性"，并让插件作者能写。

## 3. 方案比较

### 3.1 三个方案

**(a) 只有契约用例。** 一个服务的一组调用和期望结果，用 JSON 写一次。SDK 测试工具能对本语言的实现运行它；真实宿主能对任何语言、任何位置的实现运行它。不声明数据形状。

**(b) 声明数据形状。** 每个方法的参数和返回值写一份 JSON Schema，随 `provides` 报给宿主。宿主在每次调用时检查，或者只在测试里检查。

**(c) 两者分层。** 以用例为主；在用例的期望里允许引用一个 Schema 片段，用来描述"这个值只要是这种形状就行"。Schema 只出现在用例文件里，不进 `provides`，不报给宿主，运行时不检查。

### 3.2 比较

| | (a) 契约用例 | (b) 声明数据形状 | (c) 分层（Schema 只在用例里） |
| --- | --- | --- | --- |
| 作者要写什么 | 几个具体的调用和结果 | 每个方法参数和返回值的完整 Schema，每种语言都要和代码保持同步 | (a)，加上需要时的 Schema 片段 |
| 能发现的 | 用例覆盖到的输入上的一切差异：字段名、`null` 与缺省、错误名、方法形状、语义（"同样的输入返回同样的东西"） | 所有调用上的形状差异，包括没写用例的输入；发现不了语义差异（形状对、值错） | (a) 的全部；对不确定的值（id、时间）能检查形状而不只是类型 |
| 漏掉的 | 用例没覆盖的输入 | 语义；Schema 本身写得宽松时的差异 | 用例没覆盖的输入 |
| 运行时开销 | 没有（只在测试时运行） | 宿主每次调用都校验，代价按值的大小增长；只在测试里检查时没有 | 没有 |
| 内核与宿主改动 | 没有；`rutis-bridge` 加一个测试模块，`rutis-host` 加一个命令 | `provides` 格式扩展，运行时上报，宿主保存并校验；跨节点导出也要带上 | 同 (a) |
| 与原则 6（契约只约定跨边界真正需要的东西，不建通用类型层） | 符合：不新增任何声明 | 违反：每个方法的数据形状成为跨边界的声明，下一步自然是从 Schema 生成各语言的类型，就是一个类型层 | 符合：Schema 只是测试里的比较方式，不是服务的声明 |
| 与原则 8（依赖声明里只有服务名） | 符合：用例按服务名运行，不关心实现在哪、用什么写 | 依赖声明不变，但宿主多了一层"服务有形状"的知识，切换时要决定形状不同怎么办（拒绝？警告？） | 符合 |
| 维护面 | 一个文件格式，三份运行器（Node、Python、Rust） | 一个格式扩展，三个 SDK 的上报，宿主侧的校验和不匹配时的处理，节点协议 | 同 (a)，Rust 运行器多一个 Schema 校验依赖 |

### 3.3 关于 (b) 的判断

(b) 的长处是真实的：它检查每一次调用，而不只是写了用例的那几次。但：

1. 它把数据形状变成跨边界的声明，正是原则 6 拒绝的东西。原则 6 的理由仍然成立：每种语言都有自己的类型系统，跨边界的统一类型层要在每个 SDK 里维护映射，而 rutis 的值传递规则已经决定了线上能出现什么值。
2. G1 里最危险的差异是语义上的：同样的"找不到"，一个实现返回 `null`，一个抛错。两个都可以符合一份宽松的 Schema。只有具体的用例能把"这个输入应当得到这个结果"写下来。
3. 运行时校验让宿主在切换时面对"形状不同"的决定，这是新的核心行为，需要新的保证和新的故障处理。

所以本设计不选 (b)。如果以后证明用例不够，先走 (c)：Schema 只作为用例里的一种比较方式，仍然不进 `provides`。

## 4. 结论

- **采用 (a)，为 (c) 留位置。** 一个服务的契约就是一个 JSON 文件：方法形状加一组用例。不新增任何声明，不改内核，不改协议。
- **一份文件，三处运行。** Node 测试工具、Python 测试工具、Rust（嵌入的宿主和 `rutis-host contract` 命令）都能运行同一个文件，给出同样的结论。
- **比较的是跨过边界之后的值。** 用例描述的是使用方真正收到的东西，所以 `null` 与缺省、数组与 tuple 这类差异能被发现。
- **契约属于服务名，不属于某个实现。** 文件可以放在任何地方，rutis 不建注册表。
- **只在测试时运行。** `rutis-host run` 不运行契约，不因契约改变路由或门控。

## 5. 契约文件

### 5.1 示例

```json
{
  "format": 1,
  "service": "calendar",
  "revision": "2026-10-10",
  "methods": { "add": "async", "list": "async", "get": "sync" },
  "cases": [
    {
      "name": "加一个事件，再列出来",
      "steps": [
        {
          "call": "add",
          "args": [{ "title": "standup", "start": "2026-10-11T09:00:00Z" }],
          "result": { "id": { "$type": "string" } },
          "as": "added"
        },
        {
          "call": "list",
          "args": ["2026-10-11"],
          "result": [
            { "id": { "$from": "added.id" }, "title": "standup", "start": "2026-10-11T09:00:00Z", "note": null }
          ]
        }
      ]
    },
    {
      "name": "找不到时抛 NotFound",
      "steps": [
        { "call": "get", "args": ["no-such-id"], "error": { "name": "NotFound" } }
      ]
    }
  ]
}
```

### 5.2 字段

| 字段 | 含义 |
| --- | --- |
| `format` | 文件格式的版本，现在是 `1`。运行器遇到不认识的版本时拒绝运行并说明 |
| `service` | 服务名。只有名字，不写语言和位置 |
| `revision` | 可选。契约自己的修订标记，任意字符串，只出现在报告里 |
| `methods` | 方法名到 `sync` / `async`。运行器先比对实现声明的方法形状：契约里的每个方法，实现都要声明，形状相同。实现多出来的方法不算错 |
| `cases` | 用例列表，按顺序运行 |
| `cases[].name` | 用例名，出现在报告里 |
| `cases[].steps` | 步骤列表，按顺序运行 |
| `steps[].call` | 方法名，必须在 `methods` 里 |
| `steps[].args` | 参数数组，按位置传。跨语言调用只有位置参数 |
| `steps[].result` | 期望的结果（见 §5.3）。与 `error` 二选一 |
| `steps[].error` | 期望抛出的错误（见 §5.4） |
| `steps[].as` | 可选。给这一步的结果起个名字，后面的步骤用 `$from` 引用 |

文件按[质量规范](quality-standard.md) Q6.4 当作外部输入：不认识的字段、不认识的 `$` 匹配符、`call` 不在 `methods` 里，都在运行任何调用之前报错，报错指出位置（`cases[1].steps[0].call`）。

### 5.3 比较规则

期望值是普通的 JSON 值，按"跨过边界之后"的形式比较：

| 规则 | 说明 |
| --- | --- |
| 精确比较 | 对象的字段集合必须完全相同：少一个字段、多一个字段都不通过 |
| 缺省、`null`、`undefined` 互不相等 | `{"note": null}` 和 `{}` 不同。线上还有第三种值 `undefined`（TypeScript 方法不返回值、省略的参数），期望里写成 `{"$undefined": true}`。三者对使用方的写法都有影响，所以都要区分 |
| 数组按顺序比较 | 长度和每个位置都要相同 |
| 数字按数值比较 | `1` 和 `1.0` 相等。JavaScript 只有一种数字，整数和浮点的区分跨语言不成立（§10 不保证） |
| 字符串、布尔精确比较 | |

只有三个匹配符，用来处理"每次运行都不同"的值、步骤之间的依赖和 JSON 写不出的 `undefined`。它们是比较方式，不是类型声明：

| 匹配符 | 含义 |
| --- | --- |
| `{"$type": "string"}` | 值是这种 JSON 类型即可：`string`、`number`、`integer`、`boolean`、`null`、`array`、`object` |
| `{"$from": "added.id"}` | 等于前面某一步结果里的值。在 `args` 里也能用，把前一步的结果传给下一次调用 |
| `{"$undefined": true}` | 线上的 `undefined`。JSON 写不出这个值，所以需要一个写法；在 `args` 里也能用 |

以 `$` 开头的键在期望值里都是匹配符。一个服务的数据里如果真有 `$` 开头的字段名，写成 `{"$literal": {...}}`。

精确比较是有意的：使用方可能用到实现 A 多返回的字段，换成 B 就坏了。契约作者想允许额外字段，要在开放问题 §14 的决定之后才有写法。

### 5.4 错误

跨边界的错误只保证名字和消息（插件 API "值怎样传递"）。契约只比较**名字**：

```json
{ "call": "get", "args": ["no-such-id"], "error": { "name": "NotFound" } }
```

- 消息是给人看的，各语言写法不同，不比较；
- 名字由实现选择：Python 是异常类名，JavaScript 是 `error.name`，Rust 是 `Error::Remote` 的 `name`。现在 Rust 的 `native_error` 一律给出 `RustError`，所以要加一个按名字构造错误的辅助函数（§12 验收条件 8）；
- 期望 `result` 而实现抛错，或者期望 `error` 而实现正常返回，都不通过，报告写出实际得到的东西；
- 传输错误（连接断开、进程退出）、`SyncWaitCycle` 不能被期望：它们出现时，这次运行失败，并说明这不是契约差异而是运行故障。

### 5.5 同步与异步

方法形状来自 `methods`，用例里不再写。运行器按形状调用：

- `sync`：同步调用，直接比较返回值。实现返回了 Promise 或 awaitable，按形状不符报告（测试工具现在已经这样做）；
- `async`：调用后等待结果，比较等待得到的值。抛错与拒绝一样处理；
- 每一步有超时，默认 10 秒，只用于防止挂死（Q7.1.2）。超时算这一步失败，报告写明是超时。

### 5.6 第一版不覆盖的

| 不覆盖 | 原因 |
| --- | --- |
| 函数和活对象（按引用传递的参数或结果） | JSON 写不出一个回调该怎样被调用；见开放问题 §14 |
| 事件 | 契约只针对服务的方法 |
| 时间和性能 | 用例只看结果 |
| 副作用的外部可见部分（写了什么文件、发了什么请求） | 只能通过服务自己的方法观察 |
| 并发调用之间的顺序 | 步骤按顺序一个一个执行 |

## 6. 放在哪里

契约属于服务名，而服务名在不同阶段由不同的人负责。所以 rutis 只规定格式，不规定位置，也不建注册表。建议的做法：

| 阶段 | 位置 | 理由 |
| --- | --- | --- |
| 尝试：只有一个实现 | 第一个实现的项目里，`contracts/<服务名>.json` | 写实现的人最清楚该返回什么；用 SDK 测试工具跑 |
| 验证：有了使用方 | 使用方可以给同一个服务写自己的用例文件（`contracts/calendar.planner.json`），描述它依赖的那部分 | 使用方最清楚自己依赖什么；提供方把这些文件一起跑 |
| 固化：第二个实现出现 | 移到一个共享的位置：一个只放契约的仓库目录、一个包（npm、PyPI、crate 都可以，文件与语言无关），或者直接复制 | 新实现要对同一组文件通过 |

同一个服务可以有多个契约文件，运行器接受多个文件，全部通过才算通过。多个文件里 `methods` 的同名方法形状不同时，在运行前报错。

这里没有选"必须放在使用方"或"必须放在提供方"：二者在 rutis 的使用方式里都会出现，格式一致就够了，位置交给项目。这是需要维护者确认的一项（§14 决定 2）。

## 7. 怎样运行

### 7.1 Node 测试工具

```ts
import { load, runContract } from '@arcships/rutis/testing'
import contract from '../contracts/calendar.json' with { type: 'json' }
import plugin from '../src/index.ts'

test('calendar contract', async () => {
  const t = await load(plugin, { services: { store: fakeStore() } })
  await runContract(contract, t.service('calendar'))   // 不通过时抛 ContractError，消息列出每个失败的步骤
  await t.unload()
})
```

`runContract` 用 `t.service(name)` 拿到的服务，即"rutis 看到的那个"：只有声明的方法，严格模式下按跨进程规则传值。所以它比较的是跨过边界之后的值。运行器还检查 `contract.service` 与 `t.service` 的名字一致、`methods` 与 `provides` 的声明一致。

### 7.2 Python 测试工具

```python
from rutis.testing import load, run_contract

async def test_calendar_contract():
    async with load(calendar_plugin, services={"store": FakeStore()}) as t:
        await run_contract("contracts/calendar.json", t.service("calendar"))
```

接受文件路径或已解析的 dict。行为与 Node 版相同。

### 7.3 Rust：实现与嵌入的宿主

`rutis-bridge` 在 `testing` feature 下加一个 `contract` 模块：

```rust
let contract = rutis_bridge::contract::Contract::load("contracts/calendar.json")?;
let calendar = ctx.get_as::<dyn HostDispatch>(host_key("calendar")).unwrap();
rutis_bridge::contract::run(&contract, calendar).await?;   // Err 里是同样的报告
```

运行器只用 `HostDispatch`：按名字拿到服务，按名字调用方法。所以对它来说，Python 行、Node 行、远端节点的导入、宿主自己用 Rust 写的实现，都是同一种东西。Rust 实现的作者在 `cargo test` 里用它；S4 的 fixture Rust 宿主也用它。

运行器比较的是会话层的 `Value`，不是 `Value::json()` 的结果：`json()` 把 `undefined` 变成 `null`，会让 §5.3 的区分失效。

### 7.4 rutis-host contract：真实宿主与 CI

```
rutis-host contract [rutis.json] contracts/calendar.json [contracts/calendar.planner.json ...]
```

1. 按配置启动宿主（与 `run` 相同的组装）；
2. 等契约里的服务出现，最多等 30 秒，等不到时失败，并打印这一行当前的状态（与 `check` 相同的信息）；
3. 对它运行全部用例；
4. 关闭宿主，检查没有残余（Q2.4），按结果退出。

| 退出码 | 含义 |
| --- | --- |
| 0 | 全部通过 |
| 1 | 有用例不通过 |
| 2 | 没能运行：契约文件不合法、配置不合法、服务没有出现、运行中出现传输故障 |

`--json` 输出机器可读的报告，格式视为接口（Q6.6.6）。

用一份只为测试准备的 `rutis.json`，就能对任何实现运行：本地 Python 行、`peer:B/calendar` 导入、`remote` 运行时上的行。CI 里对每个实现各写一份配置，跑同一个契约文件。

契约会真实地调用服务。对生产环境的实例运行，副作用由使用者负责；文档要写明应当用测试配置（§10 不保证）。

### 7.5 报告

三个运行器给出同样结构的报告：

```
calendar（revision 2026-10-10）：2 个用例，1 个不通过
  ✗ 加一个事件，再列出来
    步骤 2 list("2026-10-11")
      result[0].note：期望 null，实际没有这个字段
  ✓ 找不到时抛 NotFound
```

路径的写法在三个运行器里相同，便于比对（§9）。

### 7.6 用契约做使用方的替身（第二阶段）

使用方的测试里常常要一个假的 `calendar`。同一个契约文件可以生成一个替身：按 `args` 匹配用例里的步骤，返回期望的结果或抛出期望的错误，没有匹配的调用抛 `ContractError`。这样使用方测试用到的数据形状，和提供方被验证的形状是同一份。它不是第一版的必需部分（§15）。

## 8. 版本与演进

- **文件格式**有 `format` 版本。新增匹配符或字段时，旧运行器遇到新文件报错并说明要升级哪个包；新运行器继续接受旧格式。
- **契约内容**有可选的 `revision`，只用于报告。rutis 不比较使用方期望的修订和提供方通过的修订：依赖声明里只有服务名（原则 8），不带版本。
- **兼容的修改**：加用例；加方法（旧实现不通过新契约，这是有意的：新方法是契约的一部分了）。
- **不兼容的修改**（改字段名、改错误名、改方法形状）：在 rutis 里没有服务的版本号，所以不兼容的修改就是换一个服务名（`calendar2`），或者在同一次配置编辑里同时换提供者和使用方。本设计不改变这一点，只是让这种修改能被契约用例发现，而不是在运行中由使用方发现。

这回答了设计哲学 §八"契约的演进"的一部分：数据形状的一致不再只靠约定，而是由一组可以对任何实现运行的用例检查；但不引入类型层，也不在运行时强制。

## 9. 与 #206 和 S4 的关系

**#206（测试工具与真实运行时一致，风险 A1）。** #206 要求同一组调用在测试工具和真实运行时上运行，结果比对。契约运行器正好提供这个手段：

1. 把 `conformance-weather` 里能写成 JSON 的部分（`today`、`later`、错误）写成一个契约文件；
2. 在 Node、Python 测试工具里对 fixture 运行；在 `rutis-host contract` 里对 Node 行、Python 行运行；
3. 四个报告应当相同。不同之处就是 #206 要找的差异，写进"允许的差异"列表。

`each`（回调）和 `crash`（进程退出）不能写成 JSON 用例，仍然留在 Rust 的一致性检查里。

反过来，契约运行器的可信度也依赖 #206：如果测试工具的严格模式与真实运行时传值不同，SDK 里通过的契约到宿主里可能不通过。所以 #206 的比对应当包括契约运行器本身。两者可以一起实现：先做格式和三个运行器，再用 weather 契约同时完成 #206 的比对。

读代码时看到的两处可能的差异，需要 #206 的比对确认：

- Node 测试工具的严格模式把普通对象里的 `undefined` 字段原样保留；真实的 Node 运行时把只含数据的对象按 JSON 编码，`undefined` 字段变成 `null`。同一个实现，在测试工具里契约会得到 `{"$undefined": true}`，在宿主里得到 `null`。这正是 K4；
- Python 测试工具里，实现抛出的异常不经过 `_cross`，测试拿到的是原来的异常对象。契约只比较名字，所以不受影响，但 #206 应当把它列为已知差异。

**S4（#188，实现迁移）。** S4 验证切换本身：切换期间调用不挂起（G2），旧实现不残留（G3），宿主不重启（G5）。G1 由契约负责。S4 里：

- 写一个 `calendar` 契约（包括 `planner` 用到的调用）；
- 三个实现（Python 行、节点 B 上的实现、Rust 实现）各自先通过这个契约；
- S4 的 fixture Rust 宿主在每个阶段切换完成后，用 `rutis_bridge::contract::run` 再跑一次，确认使用方此刻看到的服务仍然满足契约。

这样 S4 证明的是完整的一句话：换了实现，`planner` 不改，而且它看到的数据也没变。

## 10. 行为与级别

本设计不改内核，不新增核心承诺。"使用方只依赖服务名而不依赖实现"已经是核心承诺（Q3.1）；契约是它在数据层面的验证手段。

| 行为 | 级别 |
| --- | --- |
| 同一个契约文件，在 Node 测试工具、Python 测试工具、Rust 运行器上，对同一个实现，给出相同的通过与否和相同的失败路径（允许的差异写明、有界） | 契约行为 |
| 比较规则 §5.3：对象字段精确比较；缺省、`null`、`undefined` 互不相等；数组按顺序；数字按数值；`$type`、`$from`、`$undefined`、`$literal` 的含义 | 契约行为 |
| 错误只比较名字 §5.4；传输错误让运行失败而不是算作差异 | 契约行为 |
| 方法形状比对 §5.5：契约的方法实现都要声明且形状相同；`sync` 方法返回 Promise / awaitable 不通过 | 契约行为 |
| 每一步默认 10 秒超时，超时算失败 | 契约行为 |
| 契约文件不合法时，运行任何调用之前报错，并指出位置 | 契约行为 |
| `rutis-host contract` 的步骤、退出码 0 / 1 / 2、`--json` 输出格式；结束后无残余 | 契约行为 |
| `rutis-host run` 和 loader 不读取、不运行契约，契约不影响路由和门控 | 契约行为 |
| 报告的文字排版 | 实现细节 |
| 宿主在运行时检查实现是否符合契约 | 明确不保证 |
| 通过契约意味着用例之外的输入上行为也一致 | 明确不保证 |
| 整数与浮点的区分（`1` 与 `1.0`）跨语言保持 | 明确不保证：JavaScript 只有一种数字 |
| 错误消息一致 | 明确不保证 |
| 使用方期望的契约修订与提供方通过的修订相同 | 明确不保证：依赖声明里没有版本 |
| 函数、活对象、事件、并发顺序、性能被契约覆盖 | 明确不保证（第一版） |
| 对生产实例运行契约没有副作用 | 明确不保证：契约真实调用服务 |

"明确不保证"里有人可能误以为被保证的两项，要有验证锁定（Q3.4）：`rutis-host run` 不运行契约（配置里放了契约文件也不运行）；`1` 与 `1.0` 比较相等。

## 11. 风险评估

场景：插件作者用契约保证切换实现时数据形状不变（场景 G）。下表是本设计自身可能出的问题。

| # | 可能出的问题 | 维度 | 影响 | 可能性 | 级 | 控制 |
| --- | --- | --- | --- | --- | --- | --- |
| K1 | 用例太少：契约通过，实现在用例之外仍然不同 | 语义 | 高 | 高 | P0 | 无法完全自动化。控制：使用方可以加自己的用例文件（§6）；S4 的契约覆盖 `planner` 的全部调用；用户文档写明"契约只覆盖写下的用例"。残余风险记录在现状文档 |
| K2 | 三个运行器的比较规则不同：同一结果在 Node 里通过、在 Rust 里不通过，或反过来 | 语义 | 高 | 中 | P0 | 一份比较规则的一致性文件：`(期望, 实际, 结论, 失败路径)` 的列表，覆盖 §5.3 每条规则和每个匹配符；三个运行器都跑它，在合入前运行 |
| K3 | 比较规则把不同判为相同（例如 `null` 与缺省、多出的字段），漏掉 G1 的典型差异 | 语义 | 高 | 中 | P0 | K2 的一致性文件里每条规则都有反例；§12 验收条件 5 的反例实现 |
| K4 | SDK 测试工具里通过，真实宿主里不通过（测试工具传值与运行时不同） | 语义 | 高 | 中 | P0 | 与 A1 共用控制：#206 的比对包括契约运行器（§9） |
| K5 | 实现挂起，契约运行跟着挂起 | 故障 | 中 | 中 | P1 | 每步超时；`rutis-host contract` 等服务出现也有上限；测试用一个永不返回的实现 |
| K6 | `rutis-host contract` 结束后留下进程或链接 | 残留 | 中 | 中 | P1 | 与 E + R 共用残余检查 |
| K7 | Rust 实现无法给错误命名，契约里的错误名在 Rust 实现上永远对不上 | 兼容 | 中 | 高 | P1 | 按名字构造错误的辅助函数；Rust 反例与正例测试 |
| K8 | 契约文件格式变化后旧文件无法运行，或旧运行器静默忽略新匹配符 | 演进 | 中 | 中 | P1 | `format` 版本；不认识的字段和匹配符报错；格式解析的边界测试和变异测试（Q6.4） |
| K9 | 对生产实例运行契约造成副作用 | 安全 | 中 | 低 | P2 | 用户文档；`rutis-host contract` 只读用户指定的配置 |
| K10 | 契约被误用为运行时的检查，有人在 loader 里加"切换前先跑契约" | 语义 | 中 | 低 | P2 | §10 写明不保证；锁定 `run` 不运行契约的测试 |

## 12. 验收条件

每条都可以写成自动化验证：

1. 契约文件格式有说明文档（中英文）和一份描述文件本身的 JSON Schema（描述的是测试文件，不是服务）；
2. 比较规则一致性文件存在，Node、Python、Rust 三个运行器对其中每一项给出相同的结论和失败路径；
3. 格式解析：不认识的 `format`、字段、匹配符，`call` 不在 `methods` 里，多个文件方法形状冲突，都在调用之前报错并指出位置；有边界和变异测试；
4. `runContract`（Node）、`run_contract`（Python）、`rutis_bridge::contract::run`（Rust）对一个正确的实现通过；
5. 反例实现，每个只有一处不同，每个都不通过，报告指向正确的用例、步骤和路径：字段改名；`null` 变成缺省；`null` 变成 `undefined`；多一个字段；错误名不同；该抛错时返回 `null`；`sync` 声明成 `async`；实现缺一个方法；
6. 一个永不返回的方法，在超时后失败，测试本身不挂起；
7. `rutis-host contract` 黑盒测试：退出码 0、1、2 各自的情况；`--json` 输出；服务不出现时的报错；结束后残余检查通过；
8. Rust 实现可以抛出指定名字的错误，契约的 `error.name` 能与它匹配；
9. weather 契约（§9）在 Node、Python 测试工具和 `rutis-host contract`（Node 行、Python 行）上给出相同报告（与 #206 共用）；
10. `rutis-host run` 时，契约文件存在也不被读取（锁定"不保证"）；
11. S4：`calendar` 契约对 Python、节点、Rust 三个实现都通过，且在每次切换后由宿主再跑一次通过。

## 13. 组件类型

| 类型（§6） | 涉及的部分 | 要求如何满足 |
| --- | --- | --- |
| Q6.9 跨实现的服务契约 | 本设计整体 | 1. 方法形状已可声明；数据形状不以声明的方式、而以用例的方式表达（§3.3 说明为什么不按字面"声明"）。2. 同一组用例对任何实现运行（§7）。3. 替换本身由 S4 验证（§9） |
| Q6.7 插件 SDK 与测试工具 | `runContract`、`run_contract` | 两个 SDK 语义一致（验收 2、4）；与真实运行时一致（验收 9，#206）；严格模式下比较跨边界之后的值，提前暴露跨进程才出现的差异 |
| Q6.6 面向用户的入口 | `rutis-host contract` | 黑盒验证，退出码写进文档（验收 7）；`--json` 视为接口 |
| Q6.4 外部输入解析 | 契约文件 | 边界、变异测试，错误指出位置（验收 3） |
| Q6.5 资源持有者 | `rutis-host contract` 启动的宿主 | 结束后无残余（验收 7） |

Q6.9.1 写的是"数据形状必须可声明"。本设计用用例而不用 Schema 表达数据形状，§3.3 给出理由。如果维护者认为 Q6.9.1 必须字面满足，§3 的 (c) 是不违反原则 6 的满足方式：Schema 只出现在契约文件里。这一点需要决定（§14 决定 1）。

## 14. 开放问题与需要决定的

**需要维护者决定：**

1. **Q6.9.1 的解释。** 用例算不算"数据形状可声明"？如果不算，是改 Q6.9.1 的措辞，还是在第一版就加入 (c) 的 `$schema` 匹配符？本设计倾向前者：第一版只有用例，`$schema` 等真实需要出现再加。
2. **契约文件放在哪里。** 本设计只建议（§6），不规定。是否要规定一个默认位置（例如项目里的 `contracts/`），让 `rutis-host contract` 不带文件参数时自动找到？
3. **额外字段。** 默认精确比较，多一个字段不通过。是否需要一个"允许额外字段"的写法（例如对象里的 `"$extra": true`）？允许会让契约更容易维护，但会放过"使用方用到了 A 独有的字段"。
4. **用例之间的状态。** 用例按顺序对同一个实例运行，有状态的服务要靠用例自己避免互相影响（例如用不同的 id）。是否需要一个可选的"重置"约定（例如契约里声明一个 `reset` 方法，每个用例前调用）？
5. **`rutis-host dev` 是否运行契约。** 开发模式下，重载后自动对当前项目运行 `contracts/` 里的契约，会让 agent 的迭代更快发现形状变化。但这让开发模式多了一种行为。是否做、何时做？

**开放问题：**

6. **函数和活对象。** 一个参数是回调的方法（例如 `each(fn)`）怎样写成 JSON 用例？可能的写法是一个 `{"$callback": [...期望被调用的参数], "returns": ...}`，但会让格式复杂很多。第一版不做。
7. **事件。** 同名服务的不同实现发出的事件是否也要有契约？现在跨边界的事件只是通知（边界规则 §5），先不做。
8. **契约与 Cordis 挂载的生成类型。** Cordis 插件经过挂载时有从 TypeScript 生成的类型（风险 F2）。那些类型是否可以导出成契约的一部分，还没有研究。
