# 形式化验证重新设计：先把新架构的行为证明清楚

[English](design-formal-verification-2026-11-08.en.md)

状态：草案，未实现。日期：2026-11-08。
Issue：[质量跟踪 #183](https://github.com/arcships/rutis/issues/183) 第四步；实施分项 [#635](https://github.com/arcships/rutis/issues/635)、[#613](https://github.com/arcships/rutis/issues/613)、[#622](https://github.com/arcships/rutis/issues/622)、[#624](https://github.com/arcships/rutis/issues/624)、[#630](https://github.com/arcships/rutis/issues/630)、[#631](https://github.com/arcships/rutis/issues/631)、[#634](https://github.com/arcships/rutis/issues/634)、[#639](https://github.com/arcships/rutis/issues/639)。依据：[质量规范](quality-standard.md) §3、§8、§9.4、§11；[质量执行现状](quality-status.md)。

本文重新规定形式化验证的范围、顺序和完成标准。它不是“把所有代码都翻译成数学”，而是回答：**rutis 对外承诺的行为，在设计、实现、每种语言和真实运行环境中，分别由什么证据证明。**

## 1. 现在要解决什么

rutis 最近连续修改了事件、跨运行时调用、远程租约、节点托管、服务和生命周期。原来按旧架构写的模型不能直接当成新架构的证明：

- 会话帧、事件、远程接管和行生命周期的规则分散在多份旧设计里，其中有些已经标为取代；
- 当前已有的 TLA+ 模型只覆盖跨运行时同步调用和远程租约；已有的 shuttle 模型只覆盖三个历史竞态；
- #183 第四步列出的工作已经从旧的版本排期改成八个相互关联的 issue，不能再按旧的 0.11–0.14 顺序执行；
- 同一个规则可能只在 Rust 测试里验证过，其他运行时没有同一用例；也可能模型证明了设计，却没有证明实现真的按模型运行；
- 计时、平台差异、输出文字和操作系统行为不是 TLA+ 擅长的范围，却不能因此没有验证。

因此本设计先重新整理“规则是什么”，再决定“哪一种验证手段适合哪一种问题”。任何来自旧设计的模型，都必须先对照当前规格，标为**当前、已取代或明确不保证**，才能继续使用。

## 2. 决定

### 2.1 形式化验证提前到行为定稿之前

涉及多个参与者、消息交错、延迟、接管或关闭顺序的设计，先完成小模型和关键不变式检查，再定稿和实现。这是质量规范 Q9.1.2 的执行方式，不再把形式化验证当作功能完成后的附加工作。

#1025 的事件关闭接纳优化也遵循这个顺序：先把“关闭标记何时对新事件生效、已接纳事件如何 drain”写成规则并验证竞态，再实现 marker 优化。性能基准不能替代语义验证。

### 2.2 不按工具排期，按人能观察到的行为分层

工具只是手段。开发者真正关心的是消息能否正确握手、插件会不会在依赖未满足时启动、断线后会发生什么、错误是否明确。覆盖分为四层：

| 层 | 人话问题 | 主要工作 |
| --- | --- | --- |
| A. 协议基础 | 两端到底交换什么？出错、取消、超限时会收到什么？ | #635：整理会话协议规格、帧、握手、引用、取消、错误、上限和畸形输入 |
| B. 并发与生命周期 | 同时启动、调用、关闭时，会不会死锁、漏清理或多执行一次？ | #622、#630、#613：内核可控调度、各语言可控调度、事件与调用模型 |
| C. 跨进程与部署 | 断线、接管、重连、节点替换时，旧的东西会不会影响新的？ | #613、#624：远程租约、节点托管、接入点、trace validation 和跨实现一致性 |
| D. 输入与长期可靠性 | 任意值、坏帧、坏配置、长时间运行时还可靠吗？ | #631、#639：属性测试、模糊测试、Kani/Miri、虚拟时钟、一致性用例和普通测试 |

#634 是四层共用的追踪表和收口工作，不是第五种功能，也不单独代表一套模型。

以下方案明确放弃：按 TLA+/shuttle/PT 工具分别排版本，因为它会把同一条规则分散，无法说明完成；建立一个覆盖所有实现的“大一统模型”，因为它会掩盖语言调度和实现偏差；用代码覆盖率作为门槛，因为执行过不等于断言了行为；把所有规则都交给形式模型，因为平台、输出、计时和长期资源趋势必须由其他手段验证。

### 2.3 每条规则必须形成“规则到证据”的闭环

每一条核心承诺或契约行为都按以下顺序处理：

1. **找到唯一的现行来源**：在协议规格、设计或用户文档中写清楚；旧文档若仍被引用，先标注其状态。
2. **用人话写出结果**：说明正常情况、失败情况、影响范围和恢复方式；不能只写“最终一致”或“不会死锁”。
3. **列出反例**：什么交错或输入算违反规则，例如“旧会话的迟到指令装进新会话”“关闭标记提交后仍接纳新的回调”。
4. **选择能回答问题的手段**：设计问题用 TLA+，实现交错用 shuttle/可控调度，跨实现差异用一致性套件，输入空间用属性/模糊测试，计时用虚拟时钟，真实装配用黑盒测试。
5. **把证据连回实现**：测试、模型、trace 和实现文件互相标注保证编号；模型通过不等于实现已通过。
6. **故意制造一个错误**：对模型、参考实现或测试注入变异，确认验证确实能发现问题，而不是“什么都没检查到”。
7. **在适用实现和平台上运行**：Rust、Node、Python、Go、Bun、Swift、Kotlin 只在实际支持的能力和平台上列为适用；不适用必须写原因。

核心承诺还必须满足质量规范 Q8.2、Q8.3：规则层、组合层、环境层都要有证据，并至少用两种相互独立的方式验证。

## 3. 具体覆盖范围

下面的“覆盖”是要回答的问题，不是要求每一项都用同一种工具。

### 3.1 A 层：协议基础（#635）

先建立一份当前会话协议规格，替代散落在挂载、网络、值标签和运行时文档里的重复描述。至少覆盖：

- 握手、协议版本、能力声明和不匹配时的拒绝；
- 行和服务的装载、卸载、状态变化，以及未知操作；
- 调用、返回、错误的 `code` 与 `data`，同步等待标记和 `path` 转发；
- 对象/值引用的 grant、release、引用计数和会话关闭；
- 取消、超时（如果该处有承诺）和多跳传递；
- 事件发出、投递、导入/导出和取消边界；
- 消息大小、嵌套深度、字段类型、未知字段、重复/乱序/不存在引用；
- 每种错误的影响范围：只让本次调用失败、关闭会话、撤销一行，还是停止运行时；
- 线格式和能力变化的兼容规则。

这层的验收不是“有一份文档”，而是同一组协议用例在每个适用实现上得到同一类别的结果。#635 还要复现并处理已发现的对象引用疑点：对象发给不支持 `objects` 的运行时，只应按规格让这次调用失败，不能因为解码错误而无意中结束整个会话；如果现行设计选择另一种行为，必须明确写入规格和错误范围。

### 3.2 B 层：内核、事件和并发（#622、#613）

覆盖一个插件从创建到结束的完整生命周期：

- 依赖未满足时不启动；依赖消失时停止；依赖恢复时按规则恢复；
- 同一个清理动作在并发关闭、重复关闭和用户回调报错时最多执行一次；
- root、子树、实例和行的关闭顺序；关闭中的对象如何拒绝新工作；
- 事件 listener 的接纳、snapshot、取消、顺序和 panic 后继续投递；
- #1025 的关闭协议：在 admission 锁下先提交完整子树的关闭标记，再发布既有 `closing` 状态；提交后不得有新的 callback 被接纳，已经接纳的 callback 即使在提交后开始也必须按既定规则完成或退出；模型和实现测试必须覆盖 `FiberInner::lineage_closed` 的发布顺序、`Shared.admission` 下固定子树的完整标记、`closing`/marker commit 的线性化边界、parent/child/sibling 并发关闭、`Entry::live()` 不遍历祖先后的等价性、`Entry::start()` 中 `CallFlight::begin(owner)` 与最终 `live()` 检查的竞态，以及 sync/async、取消、shutdown 和跨进程行为不变；
- 服务替换、事件导入/导出、观察者和 `dispatch` 链的边界；
- 同步调用、异步投递、回调反向调用和取消是否会形成等待环；
- 资源释放：任务、引用、监听器、内部记录在关闭后回到基线。

#622 用 shuttle 和参考模型探索 Rust 实现的实际交错，补充 spawn、锁、计时替身、dispose 准入、在途卸载计数、root/子树关闭、依赖驱逐、emit 链和观察者等模型，并加强现有三个历史竞态模型。#613 的 TLA+ 模型描述参与者之间的规则，不把单进程实现细节硬塞进协议模型。

### 3.3 B 层：各语言运行时的可控调度（#630）

模型检查不能代替语言运行时自己的调度验证。对每个支持的运行时，检查它在暂停、插入和延迟帧时是否仍遵守同一协议：

- Node/Bun：帧泵、同步等待、可重入性、事件投递和取消；
- Python：事件循环、取消传播、延迟回调和关闭期间的帧处理；
- Go：关闭后写帧、引用释放、并发调用和 runtime stop；
- Swift：Task 取消、严格并发和数据竞争（含 TSan）；
- Kotlin：协程、emit 取消、深度调用和调度器交错（含 Fray/Lincheck）；
- 每种语言都验证调用号、写入原子性、snapshot 与卸载的竞态，并把不支持的能力写成明确不保证。

这里验证的是“这份实现是否按协议做”，不是证明语言运行时或用户插件本身没有 bug。

### 3.4 C 层：跨运行时、远程租约和节点托管（#613、#624）

覆盖跨进程组合中最容易出现“旧东西影响新东西”的场景：

- 跨运行时同步调用的转发、`path` 改写、可重入/不可重入组合和 `SyncWaitCycle`；
- 事件跨边界投递时的入口边界、顺序、取消和回调返回；
- 进程崩溃、会话断开、半开连接、延迟和重连时，失败只影响规定范围；
- 远端租约的建立、接管、旧会话关闭、旧行清理、新会话回应 hello 的先后关系；
- 同一 id 的并发握手和替换：旧 session 完全卸载前，新 session 不注册；旧 session 的迟到指令不能作用于新 session；
- dial/listen 停止、重连退避、稳定连接后的退避重置和握手截止时间；
- 应用托管行、节点导入的服务、能力声明、服务公告和作用域；其中服务公告保持当前 Cordis 兼容语义，不在本设计中新增 #1040 的策略拒绝；
- 运行时重启、接管、迁移后的旧进程、连接、租约和注册表残余。

#613 的 TLA+ 模型回答“设计上任何交错是否安全”；#624 的 trace validation 回答“真实实现产生的事件序列是否属于模型允许的序列”；一致性套件回答“不同语言是否按同一规则做”。三者不能互相代替。

### 3.5 D 层：输入、值、资源和长期运行（#631、#639）

覆盖模型和手写用例难以穷举的输入空间：

- 值标签、serde、`path`、握手、错误图和帧序列的属性测试；
- 跨语言值往返、不能表示的值显式拒绝、引用计数在任意 grant/release 序列下不泄漏；
- 会话帧、WebSocket/RFC 6455、行分帧、配置、patch/edit 合并和插件清单的模糊测试；
- 内核注册表、判定表、listener 分发、事件 export/import、服务公告、作用域和退避的属性测试；
- Miri 检查 Rust 的未定义行为敏感路径，Kani 检查适合有限状态证明的内核性质；不把它们宣传为整个系统的证明；
- 虚拟时钟确定性验证：本地运行时 30 秒问候截止、网络/接入点 10 秒握手截止、被拒后 30 秒再拨、连接稳定 60 秒后重置退避；
- #639 追踪表中 161 条缺失的一致性用例，以及形式化手段够不着的 18 条普通测试；
- 反复创建/关闭/重载/重连后的进程、fd、任务、线程、内存和内部记录趋势。

明确的性质用属性测试，畸形输入用模糊测试，计时用虚拟时钟，操作系统和用户可见输出用普通/黑盒测试。不能因为某项“不适合形式模型”就把它从覆盖范围删掉。

## 4. 覆盖逻辑：五种证据各自证明什么

| 证据 | 用通俗话说 | 它不能证明什么 |
| --- | --- | --- |
| 现行规格与保证登记 | 我们先说清楚到底承诺什么 | 文档本身没有证明实现正确 |
| TLA+ 设计模型（#613） | 把参与者缩小后，把消息交错一个个试，检查死锁和不变量 | 实现一定照做；模型范围外的规模；单进程细节 |
| Shuttle/可控调度（#622、#630） | 让真实代码或贴近真实代码的实现按不同顺序运行，找丢唤醒、竞态、死锁 | 所有语言、所有输入和无限状态 |
| Trace validation 与一致性套件（#624、#639） | 记录真实执行经过的步骤，再检查它是不是模型允许的步骤；同一用例在各实现跑出同一结果 | 没有走到的路径；模型没有写出的规则 |
| 属性、模糊、Kani/Miri 和普通/黑盒测试（#631、#639） | 用大量值、坏输入、边界、真实进程和平台验证剩余风险 | 不能替代协议模型，也不能证明任意并发交错 |

因此覆盖链固定为：

```text
现行规则
  → 设计模型检查（规则本身是否自洽）
  → 实现可控调度（代码是否扛得住交错）
  → trace validation（实现是否走模型允许的路径）
  → 跨语言一致性（每种实现是否遵守同一规则）
  → 属性/模糊/普通/黑盒/平台验证（输入、故障、环境和长期运行）
```

任何一环失败，都不能用另一环的“通过”掩盖。例如 TLA+ 通过但 trace 不符合，说明实现偏离设计；一致性通过但模型有死锁，说明大家一致地实现了错误规则；模糊测试通过但引用计数没有性质断言，说明只证明“不崩”而没有证明“不泄漏”。

## 5. 追踪表和状态规则

#634 作为总追踪表，至少为每条规则记录：

| 字段 | 内容 |
| --- | --- |
| 现行来源 | 当前规格/设计/用户文档和章节；旧来源是否已取代 |
| 人话承诺 | 用户能观察到的成功、失败、范围和恢复 |
| 级别 | 核心承诺、契约行为或明确不保证 |
| 适用范围 | Rust、Node、Python、Go、Bun、Swift、Kotlin；承载；平台 |
| 证据 | 模型、测试、trace、属性/FZ、黑盒、计时；具体路径/用例名 |
| 变异或反例 | 验证曾经抓到的 bug，或故意注入的错误 |
| 状态 | 已验证、部分验证、未验证、明确不保证 |
| 缺口 | 下一步 issue；不能把“未覆盖”写成“通过” |

状态的含义保持严格：模型通过只把模型列为通过；必须有实现证据才能把规则列为已验证。明确不保证的行为集中登记，避免用户把“没有承诺”误读成“偶尔有效的承诺”。

发布前的门槛：

1. 没有来自已取代设计的模型被当作当前证明；
2. 每条核心承诺都能连到现行来源、实现证据和适用范围；
3. 每条核心承诺在规则、组合、环境三个层次有证据，并至少有两种独立验证；
4. 每种适用实现都有一致性用例，跳过项写出理由；
5. 计时承诺由虚拟时钟确定性验证；
6. 模型和测试都有非空检查：故意错误必须能被发现；
7. 新增或改变的规则同步更新规格、追踪表和测试；
8. 按质量规范 Q9.4.4，发布时未验证的核心承诺为零，契约行为未验证数不超过上一发布。

## 6. 实施顺序和依赖

### 第 0 步：重新建立基线（#635、#634）

- 建立统一会话协议规格；
- 清理旧文档引用，给规则标记当前/已取代/明确不保证；
- 重新生成保证登记和追踪表的规则清单；
- 把现有 `specs/cross-runtime-sync`、`specs/remote-lease` 和 `rutis` shuttle 模型逐条对账；
- 把已知疑点（包括对象引用导致会话结束的疑点）变成可复现用例。

没有完成这一步，后续“通过”只能说明旧模型通过，不能说明新架构被验证。

### 第 1 步：先验证高风险语义（#613、#622、#630）

并行推进但共享第 0 步的规则：

- #613：事件、跨运行时调用、行生命周期、调用生命周期和节点托管行的 TLA+ 模型；
- #622：Rust 内核的可控调度模型；包含 #1025 的关闭/接纳竞态；
- #630：Node、Python、Go、Swift、Kotlin、Bun 等适用运行时的可控调度与静态检查。

模型发现的设计问题先改规格，不能直接用实现“绕过”反例。

### 第 2 步：把设计连接到真实运行（#624）

- 统一 trace 事件格式和允许的状态转换；
- 在 leases、host-gone、sync-cycles、AccessEvent 等场景接入 trace validation；
- 补 Swift/Kotlin 以及适用的 Go/Bun 等一致性列；
- 检查旧租约完全清理后才回应新 hello，不能只检查“新连接最终成功”。

### 第 3 步：补输入空间和不可模型化部分（#631、#639）

- 加入属性测试、模糊测试、Kani/Miri；
- 用虚拟时钟补齐所有计时承诺；
- 补完追踪表中缺失的一致性用例和普通测试；
- 每个发现的反例转为稳定回归测试，并在追踪表留下链接。

### 第 4 步：持续运行和发布收口（#634）

- PR 运行受改动影响的 P0 检查；
- 按 CI 触发条件和发布门运行检查：PR 运行受影响的 P0 检查，按路径触发模型任务并在已配置的 nightly/stress 计划中运行；周一 weekly run 无条件运行全部现有模型；发布前生成所需的模型、矩阵、故障、模糊、长时间和真实网络报告；
- 维护者只根据追踪表和质量规范判断“已验证”，不根据代码覆盖率或“测试跑过”判断；
- 把模型边界、跳过的平台、明确不保证和剩余风险写入质量执行现状。

## 7. 开发者看到什么

| 角色 | 成功时 | 失败时（逐字） | 记录与修复 |
| --- | --- | --- | --- |
| 插件作者 | 现有 API 和事件行为不变 | 关闭后的 Rust API：`root has been shut down`；错误种类仍为 `ErrorKind::Closed`，没有新增 `code`/`data` | 这是现有运行时错误，不是模型诊断；按原有关闭/依赖问题修复 |
| 宿主作者、部署者 | 现有命令、状态行、退出码和服务公告行为不变 | 本设计没有新的宿主错误行、退出码或 status 字段 | 不需要迁移；验证失败由贡献者在 CI 中修复 |
| 运行时作者、贡献者 | 本设计不新增运行时或验证工具输出；现有脚本、模型和 shuttle 输出保持原样 | 本设计不新增失败输出、退出码或诊断格式；不把验证诊断当成运行时输出 | 保留现有完整 log/调度用于重放；修复规则、模型或实现 |

### 插件作者

本设计不新增插件 API、配置字段、协议消息或运行时错误。现有成功路径和失败输出不变：关闭后的 Rust API 仍返回 `ErrorKind::Closed`，当前人类可见文字仍是 `root has been shut down`；本设计不新增 `code` 或 `data`，也不把验证诊断冒充运行时错误。插件作者看到的变化只有：涉及相关行为的 PR 可能多跑一组确定性模型、并发、属性或一致性检查。

### 宿主作者和部署者

本设计不改变 `rutis-host` 的命令、状态行、退出码、服务公告语义、租约语义或迁移格式。不会因为本设计新增 #1040 的公告策略、allowlist 或 policy-refused 状态。

### 运行时作者和贡献者

需要为新增规则补同一套一致性用例，并在适用的语言/平台矩阵中说明“不适用”的原因。现有 TLA+、shuttle 和其他验证工具的命令、退出码、成功输出和失败输出保持不变；本设计不新增验证工具，因此不在此承诺新的诊断文字。这些诊断不是 rutis 对插件用户的运行时输出。

### 概念预算

对插件作者、宿主作者和部署者：新增概念为零。对贡献者：只新增“规则、模型、trace、一致性用例、属性/模糊测试”六个工作概念；它们不进入运行时 API。

## 8. 兼容性与迁移

本设计阶段不修改源码、公开 API、线协议、配置、持久化格式、错误码、服务公告行为或发布版本号，因此没有用户迁移步骤。

实现阶段若发现当前行为与新模型不一致，必须先修改本设计和对应的现行规格，再决定是修实现、明确不保证，还是记录不兼容变化。不能先改代码再把模型改成“证明”新代码。

#1040 继续延期：本设计只验证当前已有的 Cordis 兼容动态服务公告行为；不设计未声明服务的宿主拒绝策略，也不把不可信插件信任边界下沉到这一层。

## 9. 风险与明确边界

### 9.1 主要风险

| 风险 | 控制 |
| --- | --- |
| 模型引用了已取代文档 | 第 0 步统一规格并逐条标来源状态 |
| 模型通过但实现没有照做 | trace validation、实现测试和跨语言一致性 |
| 只测了 Rust，其他语言偏离 | 同一套一致性用例和支持矩阵 |
| 模型状态空间太小或测试为空 | 写明边界；变异必须被捕获；扩大代表性配置 |
| 计时测试依赖机器速度 | 虚拟时钟；真实等待只做环境层补充 |
| 验证范围无限膨胀 | 每条手段必须对应风险；不做重复检查 |
| 把明确不保证误读为保证 | 集中登记并用回归测试锁定“不提供” |

### 9.2 不声称覆盖的内容

- 不证明任意用户插件业务逻辑正确，也不把进程外运行当作不可信代码沙箱；
- 不穷举无限数量的插件、节点、调用或任意长时间；模型必须公布有限边界，环境测试补充规模风险；
- 不用形式化模型替代平台、安装、真实网络、信号和长时间测试；
- 不把实现细节登记成契约；
- 不恢复已删除或已取代的旧机制作为当前承诺；
- 不为 #1040 增加新的安全策略或信任边界。

## 10. 完成定义

本设计完成，不等于所有验证已经完成。设计阶段完成的标志是：

- 覆盖范围、分层逻辑、依赖和边界已经决定；
- 每种规则知道应该用什么证据回答，且知道该证据不能回答什么；
- 现有模型和新架构的关系已经对账；
- 四层工作和八个 issue 的责任边界清楚；
- “开发者看到什么”、错误输出、兼容性和迁移结论已写明。

实施全部完成的标志是：追踪表每条适用规则都有现行来源、实现证据、适用矩阵和状态；关键模型、trace、一致性、属性/FZ、虚拟时钟、平台和长期测试均通过；发布门满足质量规范 Q13.1。
