# Calls in a session: start, run, reply, cancel, references and a closed session (TLA+)

[中文](README.md)

TLC exhausts every interleaving of a call from its start to its settlement in one session: the call number, the request arriving, the method running, the reply, a cancel, a late reply, the grant and release of a reference, and the session closing. It corresponds to the call lifecycle part of issue [#613](https://github.com/arcships/rutis/issues/613), quality standard Q11.2; the design is [session protocol](../../docs/protocol-session.en.md) §5, §6, §7, §10, the [session trace contract](../../docs/formal-trace.en.md) §3.4, §3.5, and the [formal verification design](../../docs/design-formal-verification-2026-11-08.en.md) §3.4. This is the second block of #613: the first is [`row-lifecycle`](../row-lifecycle/README.en.md) (the rows of a session). This block answers "one call from its start to its settlement", and, for [#626](https://github.com/arcships/rutis/issues/626), three more questions: whether a reader thread's write-back deadlocks when the channel is full, whether a callee answers after a cancel, and whether a synchronous call abandoned locally leaves an edge nothing can clean. It does not model forwarding across runtimes, the call chain `path`, the cycle check of the wait graph, the frame order of events, or rows hosted by a node; the synchronous wait appears only as one ghost edge for the "abandoned locally" question.

## The model

- **Participants**: the two endpoints of one session. A starts calls; B admits them, runs the method and answers. Each direction is FIFO and delayed arbitrarily long: `invoke`, `cancel` and `release` go A to B, `return` and `throw` go B to A. So a reply can still be on its way when a cancel is written, and a cancel can overtake the reply it meant to cancel.
- **A (the caller)**: `AStart` takes the next number and writes the `invoke`; `ADeliverLive` settles the call the reply names (`return` settles it with the value and its reference, `throw` with an error and no reference); `ACancel` gives up a call (writes `cancel`, settles the call with the caller's error); `AAbandon` gives up a synchronous call **without** a `cancel`; `ADeliverLate` decodes the reply of a cancelled or abandoned call, releases the reference it carries and discards it, the session going on; `ADeliverStray` handles a reply the caller can no longer place — `response for unknown call` per `SESS-41`, which ends the session; `ARelease` gives up what it holds and writes `release`; `AClose`/`ALearn` end this side.
- **B (the callee)**: `BReadInvoke` takes the call (still queued); `BRejectInvoke` refuses it as it reads it (bad arguments, too deep) and the reader writes a `throw` back; `BRun` starts the method; `BReply` answers and writes out one grant of the reference; `BDrop` drops a call cancelled while running, under the "never reply" rule, without a frame; `BReadCancel` handles a cancel — a queued call is dropped without an answer, a running one answers or is dropped by the rule, an answered one is not touched; `BReadRelease` gives up the grants named; `BClose`/`BLearn` end this side.
- **Close**: either side may close. The closing side fails the calls still waiting, clears the reference table it holds, and drops the frames still queued in both directions; the other side does the same when the channel ends (`ALearn`/`BLearn`). `closeCause` is the ghost that records which side closed first and why.
- **Channel and writer thread** (`Bound`, `Cap`): with `Bound = FALSE` there is no channel bound: a frame is queued where it is made, as in the first version of the model. With `Bound = TRUE` each direction is a channel of `Cap` frames, fed from the writer thread's unbounded queue (`aout`, `bout`) by `FlushA`/`FlushB`; the reader processes inbound frames and, where needed, writes back (below). `ablock`/`bblock` are "the reader is stuck writing this frame"; `AUnblock`/`BUnblock` finish that write when the channel has room.
- **Reader write-back** (`ReaderWrites`): `"direct"` is the shape before #1005 — the reader writes on the channel itself and blocks in `send` when it is full, so it stops reading; `"queued"` is today's — the reader hands the frame to the writer thread's queue and goes on reading. There are two reader write-backs: A's `release` when it discards a late reply (`ADeliverLate`), and B's `throw` when it refuses a call as it reads it (`BRejectInvoke`).
- **Reply after a cancel** (`Replies`): `"always"` answers a call cancelled while running as usual (the late reply is discarded and its reference given back); `"never"` drops it in `BDrop` when the method finishes, without a frame. A call cancelled while queued is never answered under either rule (`SESS-57`).
- **A synchronous call abandoned locally** (`Sync`, `Abandon`): a call `c ∈ Sync` records a wait-graph edge at A (`aedge`, a ghost) and a mark at B (`bmark`, a ghost). `AAbandon` applies to synchronous calls only (an async call's future sends `cancel` when dropped through `CancelOnDrop`; a synchronous wait has no such guard). `"keep"` leaves the waiter and the edge until the reply; `"drop"` throws both away without a `cancel`, so B's answer lands on `ADeliverStray`.
- **The caller's cancelled table**: `aTable` records what A's table holds for a call (`waiting`/`cancelled`/`abandoned`/`none`). After a cancel it is `cancelled`, cleared only by a late reply or a close; `CancelledEntriesDrain` checks it at rest.
- **Termination**: `Done` (`AllSettled`) is available only when every call is settled on both sides, no channel or writer queue holds a frame, and no reader is blocked. TLC's deadlock check can then tell "the work is done" from "both readers wait for each other", without a dummy action on every terminal state.

## Simplifications

- The scale is deliberately finite: most configurations have one caller, one callee, two calls, at most one cancel, one reference (granted once per reply, so at most two units of grants). `call-backpressure-before`/`-after` use three calls, one cancel and capacity 1 per direction: to block both readers at once, the cancelled call gives A a late reply (its write-back), the refused call gives B a `throw` (its write-back), and a third call's reply refills the other direction after the reader there has read; with two calls that path is not reachable. No reconnect, no second session, no multi-hop forwarding.
- The handshake is not modelled: the model starts with both sides greeted and the session usable. The version, the endpoint, the capabilities, the order of `hello` and the 10-second deadline are not modelled (`remote-lease` covers the takeover and the rest of the handshake); this model starts at the first call.
- The frames are `invoke`, `cancel` and `release` (A to B) and `return`, `throw` (B to A). `throw` only comes from a reader refusing a call it read; a method's own error settles as `return` does and is not modelled separately. `call`, `get`, `await`, `events.*` and `rows.*` are not modelled.
- Only "grows, never reused" of a call number is modelled: the prefix, the canonical decimal form, the 2^53 bound and "not in the frame's `path`" are not. The receiver's refusal of a number that does not grow has no reachable path either — a correct sender never repeats a number, and a repeated number is exactly the `reuseId` mutation, so the check would be dead code here.
- Protocol errors such as a `release` of a reference this side does not hold, a release count above the grants, or `call`/`get`/`await` on a reference that does not exist are not modelled: a correct side never sends them, and every `release` in the model is within the grants (the session errors have their cases in trace contract §3.3, §3.5).
- The call chain `path`, `rebase`, the session tags and the cycle check of synchronous waits (`SyncWaitCycle`) are not modelled: that is the scope of forwarding across runtimes (the `cross-runtime-sync` model). `Sync` only records an `aedge` ghost to see what a local abandonment leaves behind; it is not the whole wait graph.
- Values, error graphs, `bad-value`, `bad-frame`, the 16 MiB limit and the outbound limit (`outbound_limit`) are not modelled. `Bound`/`Cap` model channel capacity and the writer thread's backpressure only, not "over the host's limit the session ends". Value encoding and the limits are covered by trace contract §3.5–§3.7 and the property tests.
- The callee's reader write-back when it drops a queued call's imported arguments (the `Import` `Drop` writing `release`, also from the reader thread) is not modelled: calls carry no argument references. It has the same shape as `BRejectInvoke`'s `throw`.
- The duration of a method is not modelled: a call goes from `queued` to `running` to its reply, and the reply may be written at any later point, a cancel included. There is no timing and no promise about the order calls run in.
- After a close the queues in both directions are cleared and neither side reads: this is a simplification. In the implementation a frame already written to the channel may still be read before the channel ends; that interleaving is not in this model, and the conclusion below does not claim it.
- The cause of a close is not a protocol frame: each side ends its own session and the other learns it from the end of the channel. `closeCause` only tells the wrong designs ("a cancel closes the session", "an unknown call closes the session") apart.
- Memory order, real scheduling and frame encoding are not modelled; every action is atomic. `Done` stops on "no work in flight", not on a state of the implementation.

## Invariants and liveness

| Name | Content |
| --- | --- |
| `CancelKeepsSession` | A cancel never ends the session: the close that ends it is the caller's, the callee's, or the one the channel end brings (`closeCause ≠ "cancel"`) |
| `SettlesAtMostOnce` | A call is settled at most once: a reply, a cancel, a local abandonment and a session end never settle one call twice |
| `LateReplyDropped` | A late reply is discarded: a cancelled or abandoned call keeps the outcome it got, and the reply does not settle it again; each call has at most one reply to discard |
| `OwnReply` | The reply that settles a call is the reply of that call |
| `NoIdReuse` | A call number belongs to one call: no new call takes it again |
| `NoOverRelease` | A gives back only what it was granted: a grant is released, dropped or cleared once, never twice |
| `GrantsConserved` | At rest every unit B granted is still held by A or has been given back: a discarded late reply does not lose the reference it carried |
| `ClosedClearsTables` | A closed side holds no reference: A's imports are empty, B's exports are empty |
| `FailUnfinishedOnClose` | A closed session leaves no call unfinished on either side: no call is still waiting at A, and none is queued or running at B |
| `WaitingSettles` | Liveness (only in configurations without a close): a call A waits for is answered, cancelled or abandoned |
| `AbandonKeepsSession` | A locally abandoned call does not end the session: its reply is absorbed as a late reply, not `response for unknown call`; forgetting the entry requires a `cancel` |
| `CancelledEntriesDrain` | At rest, A's cancelled table has no entry that only a late reply would clear (the `BoundedTables` of #626) |
| `AbandonedCallsClean` | At rest, a locally abandoned call leaves no wait-graph edge: reading the reply clears the edge too |

Every checked property has a deliberate error next to it, and TLC must find the counterexample (`violated:<name>` in `expected.txt`):

The two reused-number configurations are two conclusions of one mutation: first the rule itself is broken (one number for two calls), then the wrong settlement that follows (a reply landing on another call). The two abandonment configurations are the same: first "forgetting it locally ends the session", then "forgetting to clear the edge leaves an edge nothing can clean".

## The configuration before the fix, and the gap

The two backpressure configurations write everything else the same way: the caller's and the callee's frames go into the writer thread's queue first and the writer puts them on the channel; the only difference is the reader's write-back — `"direct"` writes on the channel and stops reading when it is full, `"queued"` hands it to the writer. So the deadlock can only come from the reader's write-back, not from the caller's or the callee's writes.

| Configuration | Behaviour modelled | Result |
| --- | --- | --- |
| `call-backpressure-before` | Before #1005: the reader's write-back goes on the channel itself and blocks the reader when it is full | TLC finds a deadlock: `ablock = <<"release", 1>>`, `bblock = <<"throw", "c1", 3>>`, `toB = <<"cancel", "c2">>`, `toA = <<"throw", "c3", 2>>`, both full; no close, every call started and the cancel used, and nothing but the two write-backs is enabled. Freeing a direction needs the other side's reader to read, and it is stuck in its own write-back |
| `call-backpressure-after` | Today: the reader hands its write-back to the writer thread's queue; the thread that waits in `send` is the writer | No deadlock; `WaitingSettles` holds. The model pins "the reader does not write back itself"; #1005 already has this shape, so **no code change is needed** |
| `call-gap-cancel-table` | Today's caller cancelled table: an entry in `calls.cancelled` is cleared only by the late reply it is meant for | Violated `CancelledEntriesDrain`: A cancels a call still queued at B (B drops it, no reply); with every frame processed and no close, `aTable["c1"] = "cancelled"` is still there. The counterexample holds with `Replies = "always"` too, because `SESS-57` says no implementation answers a call cancelled while queued; changing the reply rule cannot remove the entry |

## Conclusion

- **A reader's write-back does not deadlock, provided the reader does not write back itself.** Before #1005 (`call-backpressure-before`), three calls, one cancel and capacity 1 per direction reach a deadlock: each reader is stuck on a write-back, both channels are full, and the reads that would free a channel belong to the other stuck reader. Today's shape (`call-backpressure-after`: the reader hands the frame to the writer thread's queue) has no deadlock and every call settles; #1005 already made the implementation this shape, so this model does not change code — it records why and keeps the regression configurations. The host's outbound limit (`SESS-75`) is not modelled; the writer queue is unbounded here, and "over the limit the session ends" is another rule, not part of this directory's conclusion.
- **Both reply-after-cancel implementations are allowed, and neither settles twice nor leaks a reference.** In `call-cancel-reply` (a call cancelled while running answers as usual) the late reply is discarded and the reference it carries is released; in `call-cancel-no-reply` (the method finishes and the call is dropped, no frame) no reply and no grant are produced. Both pass `SettlesAtMostOnce`, `LateReplyDropped`, `OwnReply`, `NoOverRelease`, `GrantsConserved` (at rest every grant is still held or given back) and the liveness property; `call-mut-late-reply-keeps-grant` shows the last one is not empty. `SESS-61` stays "not guaranteed"; this directory does not change the protocol text.
- **A synchronous call abandoned locally leaves no edge nothing can clean, provided the caller keeps the call until the reply.** Today's `request_sync` has no drop guard (`CancelOnDrop` is on async calls only), so a synchronous call abandoned locally sends no `cancel`: the waiter stays in `calls.waiting`, the reader's `reply_target` takes it out and calls `waits::returned` when the reply is read, and B's mark goes with its answer. `call-sync-abandon` passes; `call-mut-abandon-leaks` shows the edge staying if it is not cleared. Throwing the waiter and the edge away without a `cancel` makes the reply `response for unknown call` and ends the session (`call-mut-abandon-drops`), so the rule is: **keep it until the reply, or send `cancel`**; the model does not require a `cancel` for every local abandonment.
- **The #626 gap that remains: the caller's cancelled table.** `SESS-57` says a call cancelled while queued is not answered — by any implementation — while the caller must keep an entry in `calls.cancelled` to absorb a late reply. So every cancellation of a call that never started leaves an entry until the session closes: `call-gap-cancel-table` violates `CancelledEntriesDrain` with `Replies = "always"` too. No reply rule fixes this: either the callee acknowledges every cancellation (a change to `SESS-57`), or the protocol gains a cancel acknowledgement frame, or the caller uses a bounded notation (say a watermark of "cancelled, unanswered") and `SESS-41` is relaxed for a reply to a call the caller has forgotten. This task changes `specs/call-lifecycle/` only, not the protocol text or the implementations; this is left to the "write the conclusions back" section of #626.
- With the rest of the rules of §5–§7 — a number only grows and is never reused, a call settles once, a cancel drops the call and not the session, a late reply is discarded, a close fails the unfinished calls and clears the reference tables — the following still holds in the exhausted range: no call is settled twice; a cancel never closes the session; the late reply of a cancelled call does not change its outcome; a close on one side ends the other side too, and neither keeps an unfinished call or a reference; every grant made before the close is given back once. The state count of `call-healthy` (1,155) is the same as before the extension, so with the new switches off the model behaves as it did.
- What the model does not prove: the handshake and authentication; forwarding across runtimes, relays, call chains and wait cycles (`cross-runtime-sync`); the frame order of events and rows; value encoding, error graphs, limits and the outbound limit; multi-hop cancel propagation (the relay part of `SESS-59`); frames still on the channel after a close; the callee's reader write-back that releases a dropped queued call's argument references (same shape as `throw`); `PinnedTarget` (a running call keeps its object alive; there are no object values here); real scheduling, memory order and timing. This directory is one block of the #613 call lifecycle and is not evidence for the whole call protocol.

## How to run it

Java 11 or newer and `tla2tools.jar` ([v1.7.4](https://github.com/tlaplus/tlaplus/releases/tag/v1.7.4), sha256 `936a262061c914694dfd669a543be24573c45d5aa0ff20a8b96b23d01e050e88`). Do not commit the jar.

```sh
curl -sSLo /tmp/tla2tools.jar https://github.com/tlaplus/tlaplus/releases/download/v1.7.4/tla2tools.jar
TLA2TOOLS=/tmp/tla2tools.jar specs/call-lifecycle/run.sh                    # every configuration
TLA2TOOLS=/tmp/tla2tools.jar specs/call-lifecycle/run.sh call-healthy       # one configuration
TLC_WORKERS=4 TLA2TOOLS=/tmp/tla2tools.jar specs/call-lifecycle/run.sh      # limit TLC's workers
```

`run.sh` compares each configuration's outcome with `expected.txt` and exits 0 when every one matches; an outcome is `ok`, `deadlock` or `violated:<name>`. The logs and counterexamples are written under `TLC_OUT` (a temporary directory by default). CI's `specs` job matrix includes `call-lifecycle` (see [CI](../../docs/ci.en.md) §4).
